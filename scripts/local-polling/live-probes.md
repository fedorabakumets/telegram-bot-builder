# Локальная проверка Test01

Диагностика рассчитана на локальные PostgreSQL и Redis, проект 40 и запись токена 31. Она не предназначена для production. Секреты берутся из локального `.env` и базы и не печатаются.

## Без изменения состояния

```powershell
node scripts/local-polling/probe-live.mjs
node --import tsx scripts/local-polling/probe-handoff.mjs
```

Первый скрипт выполняет SQL `SELECT` внутри `BEGIN READ ONLY`, Redis `PING` и читает память процессов Windows. Не вызывает `/bot/statuses`: этот GET в текущем API выполняет reconciliation и может записывать статус и историю запусков. Поле `instances` показывает сохранённое состояние, а не доказательство работоспособности каждого обработчика. `builds` показывает метаданные, а не доказательство доступности объекта S3.

Второй скрипт без `--execute` только печатает план. Его реальный запуск подготовлен для отдельного согласованного этапа после прохождения тестов механизма.

## Совместимость проекта 40

На 11 ноября 2026 года в проекте 25 message, 1 command_trigger, 15 http_request, 9 condition, 10 keyboard, 8 input и 1 delay. У delay режим по умолчанию `blocking`, длительность 3 секунды; все восемь input без `inputTimeout`. Узлов расписания, API-триггеров, userbot и parallel_split нет. По текущему предикату генератора фоновые таймеры отсутствуют. Сценарий для проверки менять не требуется.

Старые сборки Test01 не содержат протокол `_WORKER_EXTERNAL_UPDATES_PROTOCOL`. Перед переходом нужна регенерация; нельзя просто включить переменную на старом артефакте.

## Изолированный запуск

```powershell
node --import tsx scripts/local-polling/probe-handoff.mjs --execute
```

Этот вариант уже изменяет локальное состояние: сначала читает объект из `silo-bot-builds-local`, распаковывает и сверяет SHA256, проверяет положительные protocol/safe markers; затем останавливает только token31 через API, поднимает отдельный worker, проверяет готовность, завершает его и возвращает token31 обычным API start. Конфигурация должна исходно оставаться `direct`, иначе скрипт откажет до остановки. Параметры в базе не меняются. Остальные токены не останавливаются этим скриптом.

При наличии настоящих входящих обновлений приёмник может пробудить реальный сценарий и выполнить его действия. Поэтому этот запуск нельзя использовать как обещание отсутствия внешних побочных эффектов. Сам скрипт не отправляет Telegram сообщения и не инъецирует synthetic updates. Надёжность доставки, ошибки, повторное пробуждение и лимиты проверяются отдельно на изолированных fixtures.

Если изолированный worker не завершился за 20 секунд, восстановление API start запрещено до проверки освобождения lease: нельзя создавать двух получателей одного токена. Если восстановление не удалось, требуется проверить token31 и повторить локальный start после устранения причины. Не удалять ключи очереди или lease вручную.

## Переключение без нового интерфейса

Существующий API переменных: `GET/POST /api/projects/40/tokens/31/env-variables`; обновление существующей записи — `PUT /api/projects/40/tokens/31/env-variables/:id`. Значение переключателя: `BOT_POLLING_MODE=direct` либо `ondemand`, `isSecret=0`. Затем `POST /api/projects/40/bot/restart` с телом `{"tokenId":31}`. Этот restart генерирует код заново; restore с reuse может сохранить прежний артефакт.

Изменения Python worker не загружаются в существующий процесс. Локальный watcher может самостоятельно перезапустить общий runner при редактировании файлов, поэтому стабильность PID остальных ботов нужно проверять отдельно и не считать гарантированной во время разработки.

Память Windows `rssMiB` и `privateMiB` — разные показатели; их нельзя складывать или напрямую сравнивать с Linux cgroup Railway. Локальные проверки типов не выполнялись: `getDiagnostics` в этой сессии отсутствует. Синтаксис обоих скриптов проверен через `node --check`.
