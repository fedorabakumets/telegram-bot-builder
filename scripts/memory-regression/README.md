# Локальные регрессии памяти

Запуск структурных проверок (стандартная библиотека Python):

```powershell
.venv/Scripts/python.exe scripts/memory-regression/run.py
```

Прогрев Aiogram в свежем процессе (нужны зависимости requirements.txt):

```powershell
.venv/Scripts/python.exe scripts/memory-regression/run.py --models --output output/local-runtime/memory-regression.json
```

`--traced` добавляет отдельный запуск с tracemalloc. Его RSS нельзя сравнивать
с обычным процессом: трассировщик сам занимает память. Нет подключения к Telegram,
БД или Redis; используются только синтетические данные. Секретные переменные
не передаются дочернему процессу. Скрипты не подключаются к работающим ботам.

Проверяются фактические Python-фрагменты генератора: после 10000 пользователей
реестр блокировок пуст; 20 одновременных чтений таблицы дают два SQL-запроса
и 1000 разборов JSON для 1000 строк и 20 колонок. Старое размножение JOIN
требовало бы 20000 разборов. RSS выводится справочно, без нестабильных порогов.

В CI достаточно быстрого запуска без `--models`; полный прогрев полезен после
обновления Aiogram/Pydantic. Профиль с `--traced` запускать вручную, не на проде.

Сравнение стоимости повторного импорта в двух и одном свежем Python:

```powershell
.venv/Scripts/python.exe scripts/memory-regression/hybrid_imports.py --output output/local-runtime/hybrid-imports.json
.venv/Scripts/python.exe -m unittest discover -s scripts/memory-regression -p test_hybrid_imports.py
```

Два отдельных процесса запускаются параллельно; затем один свежий процесс
выполняет тот же прогрев. Отчёт показывает сумму RSS и число копий собранных
моделей для ленивого импорта, 14 распространённых моделей и полного прогрева.
Это синтетическая стоимость дублирования библиотек: здесь нет запущенных
сценариев, Redis, Telegram или настоящего общего хоста. Корректность маршрутизации
постоянных и временных ботов проверяется отдельно тестами хоста. RSS включает
общие страницы и не равен физической памяти контейнера; при возможности для
Linux также сравнивайте PSS. Неизвестный RSS остаётся `null`, порога «100 МиБ» нет.

Холодная компиляция и загрузка готового байткода в свежих процессах:

```powershell
.venv/Scripts/python.exe scripts/memory-regression/compile_host.py --output output/local-runtime/compile-host.json
.venv/Scripts/python.exe -m unittest discover -s scripts/memory-regression -p test_compile_host.py
```

Скрипт создаёт синтетический сценарий из 40000 функций (примерно 2 МБ),
сравнивает прежний `compile` внутри хоста, текущий холодный `load_bot_code`
и повторную загрузку готового дискового кеша. Каждый путь работает в новом
Python; результаты функций проверяются после выполнения. Публикуются RSS
до чтения/загрузки, после выполнения и после удаления кода с GC, время
загрузки, системный пик RSS родителя и дополнительный сэмплированный пик.
Сэмплирование может пропустить короткие пики под GIL, поэтому для сравнения
пиков используется прежде всего `parentOsPeakKiB`.

На Linux `completedChildrenPeakKiB` показывает максимальный RSS завершённого
дочернего компилятора (`RUSAGE_CHILDREN`); на Windows это поле `null`.
Пики родителя и дочернего процесса относятся к разным моментам: складывать
их как фактический пик контейнера нельзя. Это синтетический эксперимент,
не расход настоящих ботов. Для сравнения с Railway запускайте скрипт внутри
того же Linux-образа и той же версии Python. Нет гарантии возврата RSS сразу
после GC и нет нестабильного порога «должно быть менее N МиБ».
