# Локальный стенд webhook и запуска по требованию

Стенд исследует текущую реализацию и отдельную модель запуска по требованию.
Рабочий runtime, генератор и production не изменяются. Успешный тест с пометкой
`CHARACTERIZATION` означает воспроизведение существующей проблемы, а не её исправление.

## Среда проверки

Проверено локально 11 ноября 2026 года: Windows, Node.js 24.22.1, npm 11.19.1,
Python 3.14.10 из `.venv`. В окружении установлены aiogram и aiohttp; для Python
проверок не нужны psutil или Jinja2. Основной прогон жизненного цикла выполнен
с aiogram 3.31.0 и aiohttp 3.14.5, как закреплено в requirements. Дополнительный
прогон системным Python с более ранними версиями дал то же поведение.

Redis на `127.0.0.1:6379` отвечает, но стенд не требует Redis, PostgreSQL,
действующих ботов или приложения на порту 5000. Docker CLI установлен,
но локальный Linux Engine недоступен; контейнерное сравнение не выполнялось.
Секреты из `.env` не нужны. Внешние S3 и Telegram не вызываются.

## Воспроизведение

Из корня репозитория, последовательно, чтобы измерения не конкурировали за CPU:

```powershell
node --import tsx --test scripts/local-webhook/build-cache.test.ts
node --import tsx --test scripts/local-webhook/delivery.test.mjs
node --import tsx --test scripts/local-webhook/security.test.mjs
node --test scripts/local-webhook/on-demand.test.mjs
.\.venv\Scripts\python.exe scripts/local-webhook/python-lifecycle.py
.\.venv\Scripts\python.exe scripts/local-webhook/python-startup.py
.\.venv\Scripts\python.exe scripts/local-webhook/python-memory.py
```

На Linux используйте Python подходящего виртуального окружения вместо Windows-пути.
Node-зависимости должны быть уже установлены. Для запуска Python нужны зависимости
проекта; стенд сам их не устанавливает. Для этих проверок не запускаются полная
проверка TypeScript или `npm run check`.

## Что именно проверяется

| Проверка | Область и границы |
| --- | --- |
| `build-cache.test.ts` | Настоящие `ensureCachedBuild` и `packBotBuild`, временные файлы и локальный HTTP. Проверяет прогретый кэш без скачивания, восстановление повреждения и отклонение неверного хеша. Это не измерение задержки S3. |
| `delivery.test.mjs` | Настоящий API-обработчик на временном loopback-сервере. Характеризует подтверждение и пересылку обновлений; не соединяет реальные контейнеры. |
| `security.test.mjs` | Настоящие middleware и webhook-обработчик с локальными заглушками. Характеризует текущие ограничения проверки секрета, идентификаторов и тела запроса. |
| `python-lifecycle.py` | Извлечённая ветка действующего шаблона с настоящими aiogram/aiohttp и поддельным Telegram API. Проверяет порядок регистрации, фоновые задачи и остановку. Это не полный сгенерированный бот. |
| `python-startup.py` | Пять новых Python-процессов и повторные загрузки минимальной фикстуры. Вывод сохраняется в `results/python-startup.json`. |
| `python-memory.py` | Настоящие `_start_bot`/`_stop_bot` воркера, три синтетических модуля, три цикла загрузки/выгрузки и проверка сборки модулей сборщиком мусора. Результат выводится в stdout. |
| `on-demand.test.mjs` | Изолированная модель диспетчера с поддельными сохранением и запуском. Проверяет координацию пробуждения и ограничения очереди; не является реализацией надёжной production-доставки. |

Адресные тесты завершились успешно: кэш — 4, доставка — 4, безопасность — 11,
модель запуска по требованию — 9; всего 28. Три Python-скрипта завершились
с кодом 0. Успех характеристик безопасности подтверждает воспроизведение дефектов,
а не безопасность текущего production-кода. Локальная диагностика типов
не проводилась: `getDiagnostics` в этой сессии отсутствует.

## Наблюдения и ограничения интерпретации

В локальной проверке жизненного цикла регистрация webhook происходила до готовности
слушателя. Восемь запросов получили HTTP 200 при восьми ещё не завершённых фоновых
обработчиках; после очистки aiohttp эти задачи оставались активными. Скрипт в конце
освобождает собственные задачи и ресурсы. Это подтверждает необходимость изменения
жизненного цикла, но само по себе ничего не исправляет.

Кэш сборки устраняет повторное скачивание, но не импорт Python-библиотек и создание
диспетчера. Прогретая загрузка минимального модуля и холодный старт интерпретатора
измеряются отдельно. Файловый кэш ОС не очищался, поэтому «холодный» процесс не
означает холодный диск или S3.

В последней серии медиана импорта aiogram составила 1 789 мс, готовности первого
Bot/Dispatcher — 1 810 мс, повторной загрузки фикстуры — 9,559 мс. Настоящий
`bot_code_cache` дал 3,797 мс на чтение/компиляцию без готового кэша и 0,530 мс
при попадании. Более ранняя серия давала около 3,28 с на импорт: прогрев ОС и
нагрузка существенно влияют на результат. Полное время дочернего процесса
включает повторные загрузки и GC и не является временем готовности бота.

В синтетическом тесте памяти загрузка трёх ботов повышала рабочий набор примерно
с 73 404 до 110 616 КиБ. После остановки и GC он снижался до 78 236 КиБ;
последующие циклы завершались на 81 772 и 82 876 КиБ. Все проверяемые модули
собирались GC, но aiogram оставался загруженным. Это показывает, почему выгрузка
бота внутри общего процесса не равна завершению процесса.

Эти числа относятся к одному локальному запуску на Windows и искусственным
данным. Они не предсказывают память рабочих ботов, RSS Linux, расход cgroup в
Railway или освобождение файлового кэша. Прототип не проверяет сохранность очереди
после падения, распределённые блокировки, дедупликацию между репликами, реальную
S3-задержку, расписания или совместимость состояния произвольного проекта.
До production нужны отдельные межконтейнерные проверки, надёжная очередь,
ограничение нагрузки и измерения на целевой Linux-среде.
