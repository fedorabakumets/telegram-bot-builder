# Пул соединений Postgres

## Дата: 2026-10-02

**Статус:** отложено. Проблема в коде, не в настройке конкретного сервера.

---

## В чём проблема

Панель ходит в базу через один пул в `server/database/db.ts`: `max: 10`. Одновременно выполняется не больше 10 запросов API. Остальные ждут в очереди `pg` до 20 секунд (`connectionTimeoutMillis`) и затем падают с таймаутом.

`acquireTimeoutMillis: 60000` в этом файле не работает: у `pg` такого параметра нет.

Через этот пул идут сохранения проектов, списки, статусы, логи. Сессии в него не входят, пока сессии лежат в Redis.

Боты эту десятку не делят. У каждого свой пул в `lib/templates/database/database.py.jinja2`:

```python
db_pool = await asyncpg.create_pool(DATABASE_URL, min_size=1, max_size=10)
```

Сто ботов с включённой базой могут держать до тысячи соединений к тому же Postgres. Когда у базы кончается `max_connections`, панель не получает даже свои 10 слотов.

Отдельно часть обработчиков создаёт свой `new Pool({ connectionString })` без `max` (пользователи бота, аватары). У `pg` значение по умолчанию тоже 10, и эти пулы живут рядом с основным.

Пока запросы короткие, десяти слотов панели хватает. Очередь видна, когда сохранения и тяжёлые выборки занимают все десять слотов сразу.

## Что делать

Пул панели оставить небольшим. Ботам не выдавать по 10 соединений.

1. В `server/database/db.ts` брать лимит из `DB_POOL_MAX`, по умолчанию 20. Строку `acquireTimeoutMillis` убрать.
2. В шаблоне бота поставить `max_size=2`. Боту хватает одного-двух соединений.
3. Обработчики со своим `new Pool()` перевести на общий пул панели.

PgBouncer в режиме транзакций ставится перед Postgres отдельно: сто ботов тогда не означают сто живых соединений базы. Это настройка сервера, не замена пунктов 1–3.

Роль `bot_runtime` из [bot-database-access.md](bot-database-access.md) эту задачу не закрывает. Она про права на таблицы, не про число соединений.
