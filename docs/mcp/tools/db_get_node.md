# `db_get_node`

## Назначение

Читает одну ноду целиком из live-БД по ID, включая `position` и полный `data`. Read-only.

## Когда использовать

Вызывай перед `db_update_node`, после `db_find_nodes` или для диагностики `input`/`code`/интеграционной ноды. Без `sheet_id` поиск выполняется по листам.

## Параметры

- `project_id` — number; обязательный параметр.
- `node_id` — string; обязательный параметр.
- `sheet_id` — string; необязательный параметр.

Точные типы и обязательность берутся из схемы MCP-регистрации. Перед вызовом проверь описание инструмента в MCP-клиенте; не придумывай отсутствующие поля.

## Пример вызова

```json
{
  "tool": "db_get_node",
  "arguments": { "project_id": 42, "node_id": "request-orders", "sheet_id": "main" }
}
```

## Пример успешного ответа

Ответ содержит точную текущую ноду. Используй её `data` как основу patch; не заменяй конфигурацию полями из памяти или старой документации.

## Типичные ошибки

- Переданы неизвестные или пропущенные обязательные параметры.
- `node_id` не найден.
- Указан неверный `sheet_id`.
- Прочитана нода, но агент не проверил её тип через `get_node_schema`.

## Ограничения и безопасность

Тул только читает данные или выполняет проверку; он не должен изменять проект, БД или состояние бота.
- Не трактуй отсутствие ошибки транспорта как подтверждение бизнес-корректности результата.
- Для дальнейшего изменения используй отдельный mutating-тул после проверки данных.

## Связанные инструменты

- `get_tool_docs` — получить карточку этого и связанных тулов.
- `search_tool_docs` — найти подходящие инструменты.
- `get_workflow_docs` — получить рекомендуемую последовательность действий.

## Рекомендуемый следующий шаг

Сверь тип и `data` со схемой, подготовь минимальный patch и используй `db_update_node` только по явной просьбе.
