# Запуск исполнителя при обновлении Railway

Контейнеры с одинаковым `RUNNER_ID` используют одну аренду Redis. Новый
контейнер ожидает её освобождения до 120 секунд с повтором раз в секунду.
Ожидание не удаляет и не перехватывает действующую аренду. Чтение команд и
запуск воркеров начинаются только после получения аренды.

Это позволяет предыдущему контейнеру завершиться во время обновления Railway,
не исчерпывая попытки перезапуска нового контейнера. При занятой аренде сообщение
об ожидании выводится один раз. Если старый процесс остаётся активным дольше
двух минут, новый завершает запуск с ошибкой; второй исполнитель не запускается.

`SIGTERM` и `SIGINT` отменяют ожидание, включая зависший запрос Redis.
Если ответ о захвате приходит после отмены, освобождается только собственная
аренда. Ошибка Redis не маскируется сообщением о занятом исполнителе.

Адресные проверки: `npx vitest run --config server/runner/vitest.config.ts`.
Они подключены к заданию `runtime` в CI `Split runtime`.

## Очередь аналитики и PermissionError

`ANALYTICS_SPOOL_DIR` задаёт корень локальной очереди минимальных событий.
Внутри создаются каталоги `{projectId}/{tokenId}` и SQLite-файлы
`pending.sqlite3`, `pending.sqlite3-wal`, `pending.sqlite3-shm`. В production
корень должен находиться на постоянном томе вне каталога временной сборки.
Если переменная не задана, используется `~/.botcraft/analytics-spool`.

При `PermissionError` проверяйте права ОС и явную проверку пути в коде:

1. Пользователь и группа реального процесса исполнителя должны иметь доступ
   к родительским каталогам и право создавать файлы в очереди. SQLite требует
   записи и в каталог для WAL/SHM, а не только в основной файл. Не применяйте
   `chmod 777` и не удаляйте очередь для устранения ошибки.
2. `_analytics_spool_directory` отклоняет каталог `{projectId}/{tokenId}`,
   если он является символической ссылкой или после разрешения пути выходит
   за настроенный корень. Исправление владельца файлов не меняет эту проверку.

Если в конкретном развёртывании дополнительно настроен внешний sandbox или
ограничение монтирования, проверьте и его правила. Наличие такого ограничения
нельзя определить только по классу `PermissionError`.

Проверяйте настройку на сервисе, который запускает Python-воркеры, а не только
на панели. После нормализации путь к каталогу бота должен оставаться внутри
настроенного корня. Дочерний процесс сценария сохраняет
`ANALYTICS_SPOOL_DIR` из окружения воркера, даже если его нет в индивидуальном
окружении бота; это не включает передачу остальных секретов сервера. При
диагностике сравнивайте путь на обоих уровнях. Не выводите токены, полное
окружение или содержимое событий в диагностический журнал.

Диагностика недоступной очереди указывает тип ошибки, операцию
(`home`, `resolve_root`, `validate_directory`, `mkdir`, `sqlite_connect` или
`sqlite_prepare`), ограниченный по длине путь и `errno`, если он доступен.
Текст исключения и содержимое события не журналируются; известные секреты
окружения и похожие на Telegram-токен значения в пути маскируются.
Не вставляйте секреты в имя каталога: маскирование не заменяет безопасную
конфигурацию. При файловой/SQLite-ошибке повтор выполняется через 2, 4, 8
и далее до 300 секунд; успешная попытка сбрасывает задержку. Автоматического
перехода на временный диск нет, сохранённая очередь не удаляется.

Отказ очереди не означает отказ Telegram или PostgreSQL. После неудачной
локальной записи бот всё равно пробует сохранить событие напрямую в БД.
Если оба хранилища недоступны, событие может быть потеряно. Уже сохранённые
в очереди события при ошибке доступа не удаляются и смогут быть доставлены
после восстановления доступа. Очередь не восстанавливает тексты переписки.

Для проверки исправления нужны наблюдаемые результаты: очередь открывается
под пользователем исполнителя, после повторной генерации и перезапуска
тестового бота новые ошибки доступа не появляются, а тестовое событие
записывается в аналитику. Наличие изменения в репозитории само по себе
не подтверждает исправление production.
