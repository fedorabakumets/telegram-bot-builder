# Серверный JavaScript для production

Нужен Node.js 24 (та же основная версия, что в CI и Docker). Режим разработки сохраняет прежнюю команду `npm run dev`
с `tsx watch` и обновлением клиента через Vite.

## Локальная сборка и запуск

Из корня проекта:

```sh
npm ci
npm run build
npm start
```

`build` последовательно собирает клиент и сервер. Для повторной сборки только
сервера доступна `npm run build:server`. Она создаёт `dist/server/index.js` через
esbuild; `node dist/server/index.js` запускает результат без `tsx`, npm и esbuild
в цепочке выполнения. `npm start` — удобная оболочка этой команды.

Сборка проверяет преобразование модулей, но не выполняет полную проверку типов.
Не запускайте полный `tsc` или `npm run check`: для изменённых файлов применяется
адресная диагностика согласно правилам репозитория.

У собранного сервера `NODE_ENV` по умолчанию равен `production`; явно переданное
значение сохраняется. Для локального тестирования используйте отдельную пустую базу
без токенов и экземпляров ботов: сервер автоматически восстанавливает сохранённые запуски.
Проверка `node scripts/smoke-server-build.mjs` сама создаёт и очищает такую локальную базу.
Сборка сама по себе ничего
не запускает и не обращается к Telegram.

## Ресурсы и зависимости

Файл JavaScript не является автономным дистрибутивом. Пакеты npm остаются внешними;
нужны установленные production-зависимости. Также сохраняются исходные каталоги
`server`, `lib`, `shared`, `scripts`, `migrations`, `assets`, необходимые конфигурации
и клиентская сборка в `dist`. В них находятся Python-воркер, шаблоны, SQL,
служебные скрипты и данные для экспорта. Не удаляйте их после сборки.

Штатный рабочий каталог — корень проекта (`/app` в Docker). Сохраняйте его при запуске:
генератор, миграции и загрузки используют рабочий каталог. `BOTCRAFT_APP_ROOT` позволяет
переопределить пути помощника `appPath`, но не заменяет рабочий каталог всего приложения.
Новые файловые пути добавляйте через `appPath` из `server/utils/app-root.ts`,
а не через расположение модуля: после объединения модулей оно меняется.

## Railway

Dockerfile собирает клиент и сервер на стадии builder, переносит `dist` и ресурсы
в runtime-образ, задаёт `NODE_ENV=production`. И Docker CMD, и `railway.toml`
используют `node dist/server/index.js`. Проверка доступности остаётся `/api/health`.

Изменение файлов не выполняет деплой. Перед переключением production проверьте
локальный запуск, статику, генерацию Python, экспорт архива и чтение медиа;
после деплоя сравните память при сопоставимой нагрузке. Установленный пакет `tsx`
остаётся нужен служебным командам и сам по себе оперативную память не расходует.
