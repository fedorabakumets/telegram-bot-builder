# Измерение памяти исполнителя

Диагностика добавляет структурированные JSON-снимки в журнал runtime. Она не меняет режимы
ботов, не запускает GC, не создаёт соединений с БД и не отправляет снимки Node в Redis.
По умолчанию все виды диагностики выключены. Настройки задаются в окружении сервиса
исполнителя либо локального runner; для применения требуется перезапуск соответствующего процесса.

## Память процессов и контейнера

Включить `RUNNER_MEMORY_INTERVAL_MS=30000`. В журнале искать `"type":"runner_memory"`.
Интервал ограничен диапазоном 5 секунд — 1 час; `0` или отсутствие отключают сбор.
Снимки последовательные: медленное чтение не запускает параллельные обходы.

| Поле | Значение |
|---|---|
| `node.rss` | Резидентная память процесса Node, байты |
| `node.heapUsed`, `heapTotal` | Живое использование и выделенная ёмкость кучи V8 |
| `node.external`, `arrayBuffers` | Внешняя память; `arrayBuffers` входит в `external` |
| `heapSpaces` | Использование отдельных областей V8 |
| `linux.processes` | Node и потомки, включая Python и временные обработчики |
| `rssBytes` | Резидентные страницы, общие страницы повторяются у разных процессов |
| `pssBytes` | Общие страницы распределены между всеми отображающими их процессами |
| `privateBytes` | Сумма приватных чистых и грязных страниц процесса |
| `anonymousBytes` | Анонимные страницы, перекрываются с другими показателями процесса |
| `container.currentBytes` | Память cgroup v2, включая файловые страницы и ядро |
| `container.anonBytes`, `fileBytes`, `kernelBytes` | Основные категории учёта ядра |
| `shmemBytes`, `fileMappedBytes`, `inactiveFileBytes`, `activeFileBytes` | Подкатегории, а не дополнительные слагаемые |
| `counters.events` | Незавершённые отправки событий и байты их JSON-представления; это не размер JS-объектов |
| `counters.redis` | Состояние и количество команд в очередях writer/reader/lease, без аргументов |
| `counters.fence` | Существующие соединения, простаивающие соединения и ожидания пула PG |
| `counters.workers` | Соответствие PID ключу воркера, число ботов и сборок, буферы stdin/stdout/stderr |

RSS, heap, external и файловый кеш **нельзя складывать**. PSS также не является точным
разложением cgroup: разные механизмы учёта, разделяемые страницы и разные моменты чтения.
Снимок содержит время начала и длительность; он не атомарный. На Windows доступны Node
и счётчики; Linux-поля недоступны. `null` означает отсутствие измерения, не нулевой расход.
Числа внутренней очереди Redis зависят от версии клиента; при отсутствии поля получается `null`.

## Оптимизация буферов и сборок

События передаются в Redis с ограничением 16 одновременных отправок. При 1024 ожидающих
событиях либо 1 МиБ JSON чтение stdout/stderr воркеров приостанавливается; оно возобновляется
ниже половины обоих порогов. События не удаляются и не переклассифицируются. Это обратное
давление, не жёсткая граница RSS: уже прочитанный кусок и системные события могут превысить
порог. `counters.events` дополнительно содержит `inFlight`, `queuedCount`, `paused`, `failures`.
Окончательные ошибки Redis считаются и записываются в журнал; гарантии повторной отправки
остаются гарантиями существующего транспорта. Команды Python доставляются последовательно
с ожиданием освобождения stdin; автоматический повтор при неопределённой доставке не добавлен.

Стандартное скачивание сборки выполняется потоками HTTP/HTTPS → gzip → SHA256 → временный
файл. После проверки размера и хеша файл публикуется атомарно. Попадание в кеш также проверяет
хеш потоковым чтением. `RUNNER_BUILD_MAX_COMPRESSED_BYTES` и
`RUNNER_BUILD_MAX_UNCOMPRESSED_BYTES` по умолчанию равны 256 МиБ. Лимиты останавливают
передачу/распаковку без публикации непроверенного исходника. Подготовка сборок и их удаление
разведены во времени, запросы очистки объединяются. Временный сон бота сохраняет его сборку.

Повторная загрузка актуального Python-байткода не читает исходник целиком. Проверка актуальности
сохраняет прежние Python magic, размер исходника и `mtime_ns`; повреждённый кеш пересоздаётся.
Одинаковые родительские пространства имён моделей aiogram разделяют словарь, сохраняя
приоритет локальных имён. Проверяется сборка всех моделей и совпадение сериализации с eager.

## Где Node выделяет память

Включить `RUNNER_HEAP_PROFILE=true` и перезапустить runner. После его готовности запускается
**один сеанс Allocation Sampling**, автоматически заканчивающийся через 60 секунд.
`RUNNER_HEAP_PROFILE_SECONDS` задаёт длительность от 1 до 300 секунд.
`RUNNER_HEAP_PROFILE_INTERVAL_BYTES` — средний шаг выборки, по умолчанию 32768 байт,
допустимы 16384–1048576. Меньший шаг даёт больше деталей и больше накладных расходов.
Профиль работает независимо от `RUNNER_MEMORY_INTERVAL_MS`.

В журнале появляются `runner_heap_profile_started` и `runner_heap_profile`. Итог содержит
длительность, путь файла, оценку выбранных выделений и 15 крупнейших мест по собственному
объёму, без повторного сложения дочерних вызовов. Координаты строк и столбцов начинаются с 1.
Полное дерево вызовов сохраняется в `.heapprofile` внутри
`RUNNER_HEAP_PROFILE_DIR` (по умолчанию `output/runner-memory-profiles`). Открыть файл:
Chrome DevTools → Memory → Load. В production координаты относятся к собранному `runner.cjs`;
сопоставление с исходными TS требует соответствующей карты исходников.

Это статистическая выборка живых выделений, сделанных **во время сеанса**, не точный размер
библиотеки и не вся память процесса. Освобождённые GC объекты обычно не представлены в итоговом
профиле. Импорты, завершившиеся до старта сеанса, не восстанавливаются задним числом.
Нативная память, файловый кеш и дочерние Python-процессы требуют отдельных измерений.
Профиль не содержит значений объектов; он содержит имена функций, пути скриптов и координаты.

Используется внутренняя сессия `node:inspector`, сетевой порт не открывается. Не совмещать
сеанс с другим профилировщиком кучи V8. Сеанс сохраняется и при штатной остановке runner;
при SIGKILL, OOM или потере аренды незавершённый профиль может быть потерян. Каталог/запись
могут оказаться недоступны: ошибка записывается в журнал и не останавливает ботов.
После завершения повторных сеансов по таймеру нет; для нового требуется перезапуск.
Файлы не очищаются автоматически и в контейнере без тома пропадут при замене контейнера.
Отключение для следующего запуска: `RUNNER_HEAP_PROFILE=false`.

## Где Python выделяет память

Временно включить `WORKER_MEMORY_PROFILE=true`, при необходимости
`WORKER_MEMORY_PROFILE_SECONDS=60` (30 секунд — 1 час). Перезапустить Python-воркеры.
Трассировка начинается перед загрузкой основных библиотек worker и модулей ботов.
В журнале runner искать `"type":"worker_memory_profile"`.

Отчёт содержит 15 крупнейших мест живых выделений, 15 крупнейших изменений относительно
предыдущего снимка, имя файла, номер строки, объём и число блоков. Содержимое объектов,
исходные строки, токены и окружение не записываются. Общие выделения библиотеки не означают,
что память принадлежит конкретному боту; путь к сборке помогает найти код проекта.
Профиль мастер-процесса не охватывает выделения отдельных временных process-обработчиков;
их RSS/PSS видны отдельно в дереве процессов Node.

`tracedCurrentBytes` — только видимые tracemalloc живые выделения, не полный RSS.
`tracedPeakBytes` — максимум с начала трассировки. `tracerOverheadBytes` — внутренняя
стоимость трассировщика; дополнительно удерживается один предыдущий снимок для сравнения.
Часть нативных выделений и фрагментация аллокатора не попадут в таблицу строк.
Профилирование само расходует память и CPU; создание снимка может задержать event loop.
Использовать короткими сессиями, сравнивать с baseline без профиля. Для отключения
вернуть `WORKER_MEMORY_PROFILE=false` и перезапустить воркеры.

## Как сравнивать изменения

1. Снять baseline с выключенным Python-профилем и включёнными снимками Node.
2. При неизменной нагрузке сравнить простой, запуск, активную обработку и простой после неё.
3. В отдельной короткой сессии включить профиль Python и найти растущие строки.
4. Менять одну причину за раз, сравнивать стабильное потребление, пики и задержки ответов.

По этим данным нельзя точно приписать весь расход каждому JS-пакету или разделить весь общий
Python-процесс между ботами. Файловый кеш cgroup также не сообщает, какой файл владеет каждой
учтённой страницей. Для поиска удерживающих ссылок и нативной памяти нужны отдельные снимки V8/профили нативного аллокатора
и контролируемые эксперименты; уменьшение RSS после изменения ещё не доказывает причинность.


## Лёгкие счётчики Python без трассировщика

При `WORKER_REPORT_MEMORY=true` существующий цикл отчётности раз в 10 секунд
публикует `worker_runtime_counters` со `schemaVersion: 1`. Тяжёлое профилирование
также включает этот цикл; сами счётчики не включают `tracemalloc` и не запускают GC.

Снимки поступают из постоянного `worker.py`. Общий `shared_host.py` для
process-ботов пока их не публикует: отсутствие таких строк нельзя считать нулевой
памятью. Реестр моделей охватывает `aiogram.types`, а не `aiogram.methods`;
его число не сопоставимо с полным синтетическим прогревом всех 591 моделей.

В `bots` доступны `tokenId`, `moduleCount`, `rootTaskPending`, `containers` и `pools`.
Для разрешённых словарей и коллекций измеряются только `count` и `shallowBytes`:
блокировки пользователей, кеши таблиц, контента и медиа, таймеры, расписания,
ожидающие сохранения и другие известные контейнеры. `pools.count`, `size`, `idle`
читаются из уже существующих пулов asyncpg, без новых соединений. Ключи,
пользовательские значения, токены и содержимое сообщений не выводятся.

`shallowBytes` — размер оболочки контейнера без вложенных объектов; его нельзя
трактовать как весь расход бота или складывать с RSS. Отсутствующее поле означает,
что контейнер не найден в известных модулях, а не доказанный нулевой расход.
`rootTaskPending` описывает корневую задачу бота, не все задачи event loop.

`exportedAiogramModels` и `builtExportedAiogramModels` показывают число уже
экспортированных классов `aiogram.types` и сколько из них имеют
`__pydantic_complete__ = True`. Это индикатор прогрева, а не размер моделей и не
полный реестр всех когда-либо созданных классов. Обход ограничен 100 ботами,
10000 модулями и 2048 экспортированными значениями. Проверять флаги
`botsTruncated`, `modulesTruncated`, `modelsTruncated` и длительность `durationMs`.

## Что изменено в удержании данных

- Блокировки переменных и code-узлов удаляются после последнего владельца или
  ожидающего. Отмена ожидания также освобождает запись; активные блокировки по TTL
  не удаляются, поэтому сериализация операций одного пользователя сохраняется.
- Bot Tables загружают колонки и строки отдельно, без размножения строк JOIN.
  Конкурентные обращения ожидают одно обновление кеша. Срок — 60 секунд по
  монотонным часам; пустой результат также кешируется. При ошибке загрузки прежнее
  поведение пустого результата сохраняется, повтор возможен через 60 секунд.
- `rate_counter` проверяет до 32 ключей при каждом обращении и раз в час в
  существующем цикле очистки пользовательских данных. Удаляются только полностью
  истёкшие ключи; действующие события не вытесняются. При большом числе ключей
  освобождение занимает несколько проходов.
- SQLite-соединения локального spool закрываются и при ошибках SQL, чтения и commit.
  Это не ограничивает число ожидающих сохранений. Без расширения надёжного payload
  нельзя заменять такие задачи усечённой очередью: сообщения и медиа терять нельзя.

Изменения шаблонов применяются к существующему боту после повторной генерации
и перезапуска. Уже загруженные библиотеки и построенные модели Pydantic остаются
общими для процесса: автоматического обещания вернуть RSS к стартовому значению нет.
# Доступ к лёгким счётчикам

Защищённый административный `GET /admin/api/runtime-settings/workers/counters`
возвращает последний снимок `pythonCounters` по группам. Используются существующее
соединение Redis и короткий кеш inspect; браузерное кеширование запрещено.
`null` означает отсутствие измерения, `stale` — возраст свыше 30 секунд.
Это счётчики постоянного Python, а не точное распределение RSS между всеми ботами.
