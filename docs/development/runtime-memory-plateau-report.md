# Исследование памяти общего рантайма

## Статус

Работа приостановлена по просьбе пользователя. Приёмка не завершена: основной прогон остановлен во время прогрева, до трёх нагрузочных партий. Устойчивое плато и отсутствие накопительного роста **не подтверждены**. Production не изменялся.

При остановке журнал зафиксировал 968 загрузок, включая четыре постоянных бота. После штатной очистки остались только основная задача и наблюдатели PostgreSQL/Redis; принудительный GC не применялся. CI коммита `31f6350cc4baae062ec831001d83da60080957ab` завершился успешно. Незавершённый прогон не засчитывается как приёмочный результат.

Исправления и стенд зафиксированы в коммите `31f6350cc4baae062ec831001d83da60080957ab`, черновик PR: https://github.com/fedorabakumets/telegram-bot-builder/pull/101.

## Подтверждённые причины и границы выводов

| Наблюдение | Проверка | Изменение / вывод |
| --- | --- | --- |
| RLS callback закрытого asyncpg-пула удерживал globals сценария | Настоящий PostgreSQL: при сохранённых трёх закрытых пулах после диагностического GC до изменения оставались три namespace, после — ноль | Callback получает минимальные globals и строковые идентификаторы проекта/токена. SQL области доступа сохранён |
| Linux signal handlers цикла удерживали последний остановленный Dispatcher | Десять настоящих циклов aiogram; отрицательный контроль со старым поведением проваливается | Воркер явно владеет сигналами; его боты передают `handle_signals=False`. Самостоятельный запуск сохраняет прежнюю политику |
| Временная ошибка Redis `peek` могла завершить обработку | CLIENT KILL собственного соединения, восстановление того же update без нового входящего события | Повторяется только безопасное чтение. Остановка, отмена и отказ приёмника прекращают ожидание |
| Освобождение Python-объектов не обязательно уменьшает RSS | Отдельные прогоны с weakrefs, tracemalloc и Memray | Циклический мусор и свободный heap аллокатора отделяются от живых удерживаемых объектов |

Первые два исправления убирают конкретные сильные ссылки. Сами по себе они не доказывают устранение всего наблюдавшегося на production роста.

Исправление глобального LRU `Update.event_type` уже находилось в main до этой работы. В работающем локальном процессе aiogram 3.31.0 проверены marker исправления и отсутствие LRU; снимки не вызывают getter и не подготавливают дополнительные модели.

## Нативная память и транспорт

В отдельном Linux-тесте с настоящими HTTP/TLS и Redis после 100 TLS-активаций контрольные ссылки уже исчезли. glibc показывал около 53,7 МиБ свободного heap. Диагностический GC почти не изменил RSS; последующий однократный `malloc_trim` снизил его с 134,1 до 89,2 МиБ. Это диагностический эксперимент, а не добавленный механизм работы рантайма.

В транспортном сравнении на 1000 активаций:

| Вариант | Конечный RSS, МиБ |
| --- | ---: |
| HTTP по IP | 89,96 |
| TLS + DNS, отдельные SSLContext | 112,09 |
| TLS + DNS, `MALLOC_ARENA_MAX=2` | 111,92 |
| TLS + DNS, экспериментальный общий SSLContext | 91,17 |

Во всех вариантах закрылись собственные клиенты и сессии; слабые ссылки исчезли до диагностического GC. DNS-прогоны создали двадцать executor-потоков. Ограничение числа арен заметного выигрыша здесь не дало.

Общий SSLContext **не внедрён**: он изменяем, а изменение доверенных сертификатов одним ботом не должно влиять на других. Эксперимент показывает стоимость повторных выделений, но не является готовым безопасным исправлением для нескольких пользователей.

Профилировщики сами существенно увеличивают расход памяти и время. Их RSS нельзя выдавать за обычный расход рантайма. Короткие одиночные замеры CPU/p95 не доказывают улучшение производительности.

## Сохранность событий и восстановление

Очередь обеспечивает доставку как минимум один раз. Сохранение состояния и ACK атомарны в Redis. При сбое ACK повторяется подтверждение, а не обработчик в том же процессе.

Если внешнее действие уже выполнено, а процесс погиб до ACK, после восстановления возможно повторение. Exactly-once для Telegram-отправок не заявляется. Произвольная ошибка FSM/обработчика автоматически не переигрывается вслепую: это могло бы повторить внешние побочные эффекты.

Отдельные проверки покрывают автоматическое восстановление чтения после CLIENT KILL, повтор ACK, остановку, отмену и отказ приёмника. Полный generated/RLS runtime после ошибки и отмены оставлял только наблюдателей PostgreSQL/Redis и основную задачу теста.

## Приёмочный прогон

План `output/acceptance-plan.json` зафиксирован до длительной нагрузки. SHA256:

`4747ca103a4946c9691dd58a77e820b4659a266dec94e8915ceb25bb8c305b1d`.

- Linux, Python 3.13.18, естественный GC, без профилировщиков и принудительных сборок.
- Настоящие PostgreSQL, Redis, Dispatcher и полный сгенерированный сценарий; контролируемый Telegram-транспорт.
- 50 временных ботов и четыре постоянных фоновых роли.
- Прогрев: 50 пробуждений каждому временному боту, затем контроль простоя 125 секунд.
- Три партии по 50 000 пробуждений в одном процессе; по 165 секунд простоя после каждой партии.
- Параллельность: восемь резидентных временных ботов; порядок запуска внутри группы описан в исходнике стенда.
- Снимки RSS/PSS/Anonymous, задач, пулов, клиентов, моделей, кешей и слабых ссылок; точные счётчики ответов, истории и аналитики.
- Пределы безопасности завершают тест ошибкой, а не успешной приёмкой.

Основной прогон запущен из отдельной неизменяемой копии исходников. Команда, версии и хеши находятся в `output/acceptance-primary-manifest.json`; сырые точки — в `output/full-probe-linux-acceptance-primary.jsonl`.

Фоновые данные анонимные и синтетические: 84 записи контента, три таблицы со 118 строками, два пользователя и 29 file_id. Они воспроизводят известные возможности сценариев, но не считаются точной копией объёмов production. Расписание действительно выполняет сгенерированный обработчик.

## Что ещё необходимо для завершения

1. Завершить три партии и оценить поздний наклон/остаточную память по заранее заданному допуску.
2. Повторить проверку в свежем процессе без изменения условий ради результата.
3. Проверить CPU и задержки в сопоставимом Linux A/B; короткие шумные замеры не подменяют этот пункт.
4. Получить зелёный CI актуального коммита и независимый аудит исходных артефактов.
5. Дополнить этот отчёт окончательными графиками, командами воспроизведения и явными ограничениями вывода.

Подготовлен также Python 3.12.16, ближе к версии production. glibc WSL 2.39 отличается от Bookworm 2.36: одинаковый расход Linux/Windows и точное совпадение с Railway не обещаются.
