# Режим работы обработчика бота

В настройках конкретного бота поле **«Работа обработчика»** управляет временем жизни обработчика. Оно не заменяет выбор способа получения обновлений: polling или webhook.

| Название в интерфейсе | Значение | Поведение |
| --- | --- | --- |
| Всегда активен | `direct` | Обработчик постоянно в памяти и получает обновления обычным способом. Пробуждение перед ответом не требуется. |
| Засыпает при простое | `ondemand` | Общий polling-приёмник сохраняет обновления в Redis и пробуждает обработчик. После простоя сценарий выгружается, но общие библиотеки остаются в памяти воркера. |
| Освобождает память после простоя | `process` | Общий приёмник запускает отдельный процесс обработчика. После простоя процесс завершается, и его память возвращается операционной системе. |

У режимов со сном первый ответ после простоя может задержаться. Общий приёмник продолжает работать: нулевой расход памяти на бота не гарантируется. Для расписаний, фоновых таймеров, API-триггеров и userbot используйте «Всегда активен». Подробные ограничения очереди и сохранения состояния описаны в [документации polling с пробуждением](on-demand-polling.md).

## Сохранение и применение

В общей форме настроек изменение сначала попадает в черновик и записывается кнопкой сохранения. Само сохранение не останавливает и не запускает бота. Для применения нужен явный перезапуск. Статус «работает» относится к текущему исполнению, а выбранное значение — к следующему запуску.

Значение хранится в PostgreSQL в `bot_env_variables`: `token_id` указывает конкретного бота, `key` равен `BOT_POLLING_MODE`, `value` содержит `direct`, `ondemand` или `process`. Отдельное поле в `bot_tokens` и миграция схемы не требуются. Значение не является секретом.

Приоритет настройки: индивидуальная переменная бота, затем переменная окружения сервера `BOT_POLLING_MODE`, затем `direct`. Дополнительный серверный фильтр `BOT_ON_DEMAND_TOKEN_IDS` может оставить бота вне списка в обычном режиме; это ограничение развёртывания, а не отдельный выбор пользователя. Подробности настройки фильтра находятся в документации polling.

Для webhook доступны только постоянно активные обработчики. Интерфейс блокирует варианты со сном, а сервер проверяет сочетание повторно. Проверяется также итоговый пакет сохранения: нельзя обойти ограничение, одновременно изменив способ получения обновлений и режим обработчика.

## API и синхронизация

Чтение и отдельная запись: `GET` и `PUT /api/projects/:projectId/tokens/:tokenId/runtime-settings`. Тело записи содержит только `{ "mode": "direct" }` с нужным значением. Ответ содержит `mode`, `source` (`bot`, `server` или `default`), `launchMode` и `requiresRestart: true`. API не возвращает токен Telegram или секреты окружения. Доступ проверяется штатной защитой проекта и токена.

Общая форма использует существующий пакетный API `PUT /api/projects/:projectId/tokens/:tokenId/env-batch`. Сохранение режима должно проходить ту же серверную проверку допустимых значений и совместимости с webhook.

После успешной записи сервер публикует `token_updated` с `changedFields: ["pollingMode"]`. Подписанные клиенты повторно загружают настройку и связанные данные; при восстановлении WebSocket-соединения кэш настроек проекта также инвалидируется. Событие сообщает об изменении конфигурации, а не о фактическом переключении работающего процесса.

## Проверка без переключения работающих ботов

Открытие настроек, чтение API и просмотр списка вариантов не меняют режим. Для визуальной проверки используйте эти действия без сохранения. Проверку записи проводите на отдельном тестовом токене; реальные работающие боты не нужно переключать ради проверки формы.
