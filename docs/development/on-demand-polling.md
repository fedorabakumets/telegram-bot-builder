# Polling с пробуждением обработчика

Настройка конкретного бота доступна в интерфейсе в поле «Работа обработчика»; см. [описание UI, сохранения и синхронизации](bot-runtime-mode-ui.md). Серверные значения по умолчанию по-прежнему задаются переменными окружения. По умолчанию `BOT_POLLING_MODE=direct`: запускается обычный polling бота.

Для постепенного включения:

```dotenv
BOT_POLLING_MODE=ondemand
BOT_ON_DEMAND_TOKEN_IDS=31
BOT_ON_DEMAND_IDLE_SECONDS=30
BOT_ON_DEMAND_MAX_ACTIVE=4
```

`BOT_ON_DEMAND_TOKEN_IDS` содержит идентификаторы записей токенов конструктора, а не Telegram ID ботов. При пустом списке режим распространяется на все подходящие polling-боты. При `direct` список не включает новый режим сам по себе. Бот вне списка продолжает обычный polling.

Значения площадки дополняют словарь окружения конкретного бота. Явные значения в существующих переменных бота имеют приоритет. Настройки передаются локальному процессу, контейнеру и удалённому исполнителю. После изменения настроек перезапустите затронутых ботов; при изменении настроек самого процесса также перезапустите воркер/исполнитель.

В режиме `ondemand` общий приёмник сохраняет обновления в Redis и пробуждает обработчик нужного бота. После простоя обработчик освобождает свои ресурсы; приёмник продолжает получать обновления. Для каждого токена остаётся отдельный запрос Telegram `getUpdates`. Общая библиотека Python и сам воркер остаются в памяти, поэтому расход памяти не становится нулевым.

Redis обязателен. Адрес берётся из уже подготовленного окружения конкретного бота: его собственной настройки `REDIS_URL` либо существующего серверного/удалённого значения по умолчанию. Подключения и секреты панели не добавляются в общее окружение Python-процесса. Пользовательский код бота не получает дополнительных серверных секретов.

Очередь одного Telegram-бота ограничена 1000 ожидающими обновлениями и 8 МиБ их содержимого. При переполнении приёмник удерживает полученный пакет и повторяет сохранение, не подтверждая его Telegram и не вытесняя необработанные записи. Не используйте вытеснение ключей Redis для этой очереди: сохранность обновлений зависит от настроек персистентности и доступной памяти Redis.

После успешной обработки сохраняется снимок `user_data`, а исходное обновление подтверждается в той же атомарной операции Redis. Это сохраняет промежуточные ответы и состояние форм между засыпанием и пробуждением. До обработки нового обновления состояние восстанавливается в свежий модуль бота.

Снимок — типизированный JSON размером до 2 МиБ: словари со строковыми и целочисленными ключами, списки, строки, числа, логические значения и `null`. Исполняемые объекты и клиенты соединений не сериализуются. Если типы, сложность или размер состояния не позволяют сохранить снимок, обработчик остаётся в памяти, а обновление не подтверждается. В журнале появляется явное сообщение; новые обновления этого бота ожидают устранения проблемы. Такую ошибку нельзя считать обычным засыпанием или успешно завершённой обработкой.

Доставка имеет семантику «как минимум один раз»: при сбое между внешним действием обработчика и атомарным сохранением состояния возможен повтор. Для платежей и других чувствительных операций нужна идемпотентность. Снимок защищает `user_data`, а не произвольные глобальные объекты Python. Перед эксплуатацией проверьте сохранность Redis и восстановление после остановки исполнителя.

`BOT_ON_DEMAND_MAX_ACTIVE` ограничивает число активных обработчиков в одном Python-воркере, а не суммарно по всем исполнителям. Одновременно работающие боты сохраняют отдельные очереди. Настройки webhook и `ondemand` вместе недопустимы: переключайте только polling-ботов.

Допустимый простой — от 0,1 до 86400 секунд, предел активных обработчиков — от 1 до 64. Несовместимые настройки отклоняются при запуске. Для ботов одного воркера используйте одинаковый предел активных обработчиков.

Перед включением пересоберите бота: сборка должна содержать протокол внешних обновлений. Боты с планировщиками, API-триггерами, userbot и другими фоновыми таймерами не допускают выгрузку: оставьте для них `direct`. Режим не заменяет постоянный процесс для задач, которые должны срабатывать без входящих обновлений.

Для отката установите `BOT_POLLING_MODE=direct` у бота или на площадке и перезапустите его. Не запускайте для одного Telegram-токена параллельные независимые получатели обновлений.

При непустой очереди запуск `direct` отклоняется: сначала верните `ondemand` и обработайте накопленные обновления. Если `REDIS_URL` настроен, но Redis недоступен, проверка не пропускается: запуск `direct` также отклоняется, поскольку проверить очередь безопасно невозможно. Если другой polling-процесс ещё удерживает блокировку бота, сначала завершите его и повторите запуск.

При пустой очереди сохранённый снимок переносится в `direct` до приёма обновлений и под polling-блокировкой. Для этого тоже требуется новая сборка с протоколом переноса состояния. После успешного восстановления снимок удаляется из Redis. Дальнейшие обновления обычного `direct` сохраняют существующее поведение: новый механизм не добавляет им долговечную очередь и атомарные снимки после каждого сообщения.


## Локальный эксперимент с временными процессами

`BOT_POLLING_MODE=process` использует тот же общий приёмник, очередь Redis и ограничения, но запускает обработчик в отдельном дочернем Python-процессе. После простоя дочерний процесс завершается: память его сценария и библиотек возвращается операционной системе. В родительском приёмнике сценарий не импортируется. В интерфейсе режим называется «Освобождает память после простоя».

```dotenv
BOT_POLLING_MODE=process
BOT_ON_DEMAND_TOKEN_IDS=31
BOT_ON_DEMAND_IDLE_SECONDS=30
BOT_ON_DEMAND_MAX_ACTIVE=4
```

Это локальный эксперимент, а не автоматическая настройка production. Все требования к Redis, совместимости сборки, порядку обработки и восстановлению состояния выше распространяются и на `process`. Завершение процесса не даёт гарантии ровно нулевого расхода на бота: родитель хранит регистрацию токена и поддерживает запрос Telegram. Базовая память общего приёмника также остаётся.

Для сравнения памяти учитывайте сумму RSS родителя и всех дочерних обработчиков в один момент времени. Показатель только родителя во время обработки скрывает действительный расход. Отдельно измеряйте исходный приёмник без ботов, ожидание зарегистрированных ботов, пик обработки и состояние после завершения всех дочерних процессов. На Windows рабочий набор, private bytes и Linux cgroup memory различаются и напрямую не сравниваются.

Чтобы убрать библиотеки, уже загруженные старым общим воркером, недостаточно перезапустить одного бота: остановите всех ботов его воркера, дождитесь завершения родительского процесса и запустите их снова в выбранном режиме. Такой перезапуск прерывает все боты этого воркера и выполняется явно. При переключении не запускайте два получателя одного токена одновременно. Новые сообщения до обработки остаются в Redis; атомарное подтверждение происходит после сохранения состояния обработчиком.

Для отката сначала остановите процессный режим и дождитесь завершения его приёмника и дочерних обработчиков. Затем применяйте правила возврата в `direct` выше: непустую очередь сначала обработайте в `process` или `ondemand`. После аварии повтор последнего сообщения допустим; это доставка как минимум один раз.
