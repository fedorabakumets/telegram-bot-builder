# Общий Python-хост постоянных и временных ботов

Настройка `RUNNER_PYTHON_HOST` задаёт топологию Python в исполнителе. Она не меняет сохранённый режим бота, транспорт, группировку или таймер простоя.

| Значение | Поведение |
| --- | --- |
| `split` (по умолчанию) | Постоянные сценарии и временные обработчики Node используют раздельные Python-процессы. Сохраняется прежний путь. |
| `unified` | Постоянные и временные сценарии группы используют один Python-хост, переиспользуя интерпретатор и библиотеки. |

Для явного включения единого хоста нужны совместимые настройки окружения **runner**:

```env
RUNNER_PROCESS_POLLING=node
RUNNER_PROCESS_HANDLER=shared
RUNNER_PYTHON_HOST=unified
```

При `unified` другие значения приёмника или обработчика отклоняются при запуске. Неизвестные значения топологии также считаются ошибкой; пустое значение сохраняет `split`.

Постоянный сценарий удерживает общий процесс. Временный сценарий выгружается после завершения обработки и простоя; его сон не останавливает постоянных соседей. Когда загруженных сценариев не остаётся, общий Python может завершиться. Нулевой расход всего контейнера и конкретная экономия памяти не гарантируются.

Общий процесс также означает общую зону отказа: завершение Python затрагивает всех загруженных соседей группы. Для возврата к прежней топологии установите `RUNNER_PYTHON_HOST=split` и штатно перезапустите runner. Перед переключением старый владелец должен завершить обработку: нельзя оставлять два получателя одного Telegram-токена. Очереди Redis и сохранённое состояние при этом не удаляются.

## Режим бота и топология — разные настройки

`direct` сохраняет сценарий и фоновые задачи в памяти. `process` оставляет приём
обновлений в Node, а Python-сценарий загружает по событию и выгружает после простоя.
Общий хост не превращает постоянного бота во временного и не обходит проверку
совместимости расписаний и фоновых операций с выгрузкой.

`RUNNER_PROCESS_HANDLER=isolated` остаётся отдельным вариантом для выделенного
интерпретатора временного бота. Он используется с `RUNNER_PYTHON_HOST=split`;
совместное значение `unified` отклоняется при старте. Единый хост не обеспечивает
изоляцию исполнения произвольного Python-кода: блокировка event loop, авария или
зависшая очистка могут затронуть соседние сценарии.

## Что измерять при включении

RSS общего Python учитывается один раз на группу; число ботов и сценариев не
является числом интерпретаторов. Выгрузка временного сценария освобождает его
ссылки и ресурсы, но не выгружает общие библиотеки и не гарантирует возврат RSS к
стартовому значению. Обещания «100 МиБ на общий Python» или «0 МиБ на спящего бота»
не следуют из выбора топологии.

Сравнивать `split` и `unified` следует с одинаковыми сборками, окружением, числом
ботов и последовательностью событий, без тяжёлого трассировщика:

1. Простой с постоянным ботом и спящими временными ботами.
2. Одновременная обработка постоянного и двух временных ботов.
3. Сон временных ботов при продолжающейся работе постоянного.
4. Остановка последнего постоянного бота после завершения всех временных.
5. Повторное пробуждение, сбой Redis и аварийное завершение Python.

Для каждого этапа сохранять PID, RSS/PSS, память cgroup, число загруженных
сценариев и задержку ответа. Остановка одного бота не должна останавливать
соседей, запускать повторный polling того же токена или подтверждать сообщение
до завершения существующего пути сохранения состояния.

Показатели памяти процессов не складываются с файловым кешем контейнера.
Подробнее о границах диагностики: [измерение памяти исполнителя](runtime-memory-diagnostics.md).
