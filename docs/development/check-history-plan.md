# История проверок личных чатов и ботов

Подготовлено по результатам исследования восьми субагентов и реализовано в миграции `0043_check_history.sql`, маршрутах `server/routes/check-history/` и компонентах `components/check-history/`. Миграция применена локально. Ниже сохранены архитектурные решения; фактический контракт находится в `shared/check-history.ts`, параметры kind используют `private-chats` и `telegram-bots`.

## Хранение

Использовать существующие `chat_access_check_jobs` и `chat_access_check_batches` для личных чатов. Добавить отдельные `telegram_bot_check_runs` и `telegram_bot_check_items` для самих ботов. Общий интерфейс истории объединяет эти источники без дублирования записей.

| Таблица | Изменения |
| --- | --- |
| chat_access_check_jobs | Снимки названия/username/исторического ID бота, безопасный failure_reason; индекс project_id, token_id, created_at DESC, id DESC |
| chat_access_check_batches | started_at, finished_at, failure_reason; индекс project_id, created_at DESC, id DESC |
| telegram_bot_check_runs | id, project_id, scope_token_id, scope_name, status, created_at, started_at, finished_at, updated_at, total_count, processed_count, available_count, unavailable_count, error_count, failure_reason, worker_id, lease_until |
| telegram_bot_check_items | run_id, token_id как исторический ID, name, username, status, reason, method, error_code, started_at, finished_at; PK run_id, token_id |

Все даты — TIMESTAMPTZ. Удаление проекта удаляет историю. Удаление бота не должно удалять прошлые проверки: текущий каскадный FK jobs→bot_tokens заменить с сохранением исторического ID и снимка подписи. Для живой связи допустим отдельный nullable FK с ON DELETE SET NULL; рабочие DTO очереди и исторические DTO разделить.

Статусы выполнения: pending, running, cancelling, cancelled, completed, failed. Историческое прерывание кодировать failed + failure_reason=server_interrupted. Completed означает завершение обработки, а не отсутствие ошибок элементов. Частичные итоги сохраняются при отмене и сбое.

В деталях ботов pending/running/available/unavailable/error. Причины — только разрешённые коды существующего TelegramBotCheckItem. Не хранить секреты, адреса запросов, команды, сырые ответы Telegram и исключения.

## Миграция

Следующий файл: `migrations/0043_check_history.sql` (перепроверить номер перед реализацией).

1. Создать новые таблицы и индексы идемпотентно.
2. Изменения legacy-таблиц выполнять с проверкой to_regclass: SQL-миграции идут раньше их bootstrap, batches сейчас создаётся лениво.
3. Добавить безопасные снимки имеющихся ботов без перезаписи уже сохранённых исторических значений.
4. Для batch восстановить начало по MIN(started_at) детей, конец по MAX(finished_at) только при завершении всех детей. Неизвестные даты оставить NULL.
5. Не создавать фиктивные старые проверки ботов из текущего authorization_error: прежние запуски не сохранялись.
6. При повторном применении не менять существующие даты и не дублировать строки. Runner выполняет все SQL при каждом старте; журнал миграций не используется.

Проверять в отдельной временной схеме PostgreSQL: свежая база, существующие jobs без batches, повторное применение, удалённые боты, незавершённые задачи. Общую миграцию рабочей базы для тестирования не запускать.

## API

Единая область чтения: `/api/projects/:projectId/check-history`.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | /check-history?kind=private_chats\|telegram_bots&tokenId=10&limit=20&cursor=… | Краткий список запусков |
| GET | /check-history/:runId | Сохранённые итоги и подробности по ботам |
| GET | /telegram-bot-checks/active?tokenId=10 | Восстановление текущей проверки ботов без нового запуска |

Существующие POST запуска и отмены сохранить. В поток прогресса добавить runId и даты; существующий обычный JSON оставить совместимым. Идентификатор общего API включает источник: chat-job:ID, chat-batch:ID, telegram-bots:ID.

Список: items и nextCursor. Limit по умолчанию 20, максимум 50. Курсор — проверенная тройка created_at/source/id, порядок убывающий и стабильный. Общий список исключает дочерние jobs, уже входящие в batch.

Запись списка: id, kind, status, createdAt, startedAt, finishedAt, scope, summary, failureReason. Даты ISO UTC. Scope содержит снимок проекта/бота и режим all_bots/selected_bot. Summary личных проверок имеет unit=bot_chats: количество связей пользователь–бот, а не уникальных людей. Для ботов unit=bots.

Детали: run и details.jobs для чатов либо details.items для ботов. Фильтр tokenId включает участие бота в общей проверке; общий итог запуска явно отделяется от результата выбранного бота. Не включать полный список ботов в каждую строку списка: загружать детализацию отдельно.

Все маршруты используют requireProjectAccess и WHERE project_id=$1. Чужие детали — 404. Валидировать kind, ID, limit и cursor. Ответы no-store. Чтение истории не вызывает Telegram и не изменяет состояние задач.

## Запись результатов и восстановление

- Создавать запуск и ожидающие элементы до первого Telegram-запроса.
- Сохранять каждый результат транзакционно до публикации прогресса; блокировать строку запуска при пересчёте итогов четырьмя worker.
- Добавить отдельный await onItem; существующий синхронный onProgress проглатывает ошибки и не подходит для сохранения истории.
- Публиковать complete только после фиксации завершения. Сбой хранения не выдавать за сохранённый результат.
- Дедупликация и резервирование ботов — в БД; all+single не должны одновременно проверять одного бота одного проекта.
- Использовать worker_id/lease_until для восстановления: отсутствие задачи в локальном Map другого процесса не доказывает перезапуск.
- Просроченные задачи помечать прерванными с частичными итогами; автоматически повторять Telegram-действия после перезапуска не следует.
- У batch сохранять число failed/cancelled дочерних задач; completed не отображать как «всё успешно» при их наличии.

## Окна истории

Оба сценария получают компактные разделы текущей проверки и истории. Строка: дата/время, область, длительность, состояние, цветные итоги. Раскрытие строки показывает результаты по ботам и причины ошибок. Цвета из shared/status-appearance.ts. История доступна после reload; закрытие окна не отменяет проверку.

Не обещать персональную детализацию старых проверок: сейчас сохраняются агрегаты задач, а chat_access содержит только последнее состояние пользователя.

## Проверки реализации

Проверить повтор миграции, сохранность после удаления/переименования бота, независимость старых итогов от новых запусков, конкурентные all+single, запись прогресса до отправки, отмену и рестарт, пагинацию при одинаковых датах, изоляцию проектов, отсутствие секретов, совместимость JSON/NDJSON.

Адресные конфиги: `server/routes/users/vitest.config.ts` для серверных тестов, основной Vitest для React. Сборки: `npm run build:server`, при изменении окон `npm run build:client`. Полные tsc и npm run check запрещены. getDiagnostics использовать только для изменённых файлов, если доступен.
