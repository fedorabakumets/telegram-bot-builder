# Приём polling в Node для временных Python-обработчиков

Экспериментальный путь убирает постоянный Python-диспетчер для ботов с транспортом polling и режимом `process` («Освобождает память после простоя»). Общий runner Node получает обновления Telegram, сохраняет их в Redis и запускает Python только для обработки очереди. После простоя Python завершается. Память самого runner и приёмников остаётся; нулевая память всего сервиса не обещается.

## Переключатель

Настройка окружения **runner**, а не отдельного бота:

```env
RUNNER_PROCESS_POLLING=node
```

По умолчанию используется `python`: прежний путь остаётся доступен. Выбор режима конкретного бота по-прежнему хранится как `BOT_POLLING_MODE=process`; новый переключатель не меняет эти сохранённые настройки. Боты `direct`, `ondemand` и неподходящий транспорт остаются на прежнем пути. В одной группе допустимы оба вида исполнителей.

Не меняйте переключатель у работающего runner без штатной остановки: старый приёмник и его обработчик должны завершиться до запуска нового владельца. Возврат на `python` требует такого же управляемого перезапуска. Очереди и снимки состояния при переключении удалять нельзя.

### Общий обработчик сценариев

При `RUNNER_PROCESS_POLLING=node` способ обработки задаётся отдельно:

```env
RUNNER_PROCESS_HANDLER=shared
```

Значение по умолчанию `shared` использует общий Python-процесс группы: интерпретатор и импортированные библиотеки переиспользуются, а сценарий и состояние каждого бота загружаются отдельно. `isolated` сохраняет отдельный временный Python-процесс для каждого активного бота. Общий процесс запускается лениво — при первом обновлении, которое нужно обработать. Сам запуск ботов и ожидание обновлений не требуют постоянного Python-процесса этого пути.

После простоя конкретного бота выгружается его сценарий. Пока хотя бы один бот группы остаётся активным, общий процесс и его библиотеки сохраняются. Когда все сценарии завершили обработку и выгрузились по таймеру простоя, общий Python-процесс завершается. Следующее обновление снова требует холодного запуска. Node-приёмник, его polling-запросы и регистрация ботов продолжают работать: отсутствие Python не означает нулевой памяти всего runtime.

Общий обработчик `shared` действует по умолчанию: границы общего процесса задаёт существующая группировка `WORKER_GROUPING` (`project`, `owner`, `shared`). Второго публичного выбора группировки нет. Настройка относится к runner и не добавляет новый режим в БД или интерфейсе: у бота остаётся `BOT_POLLING_MODE=process`, его настройки транспорта и простоя не меняются. Ветви `direct`, `ondemand` и прежний Python-приёмник этим переключателем не выбираются. Для технического отката установите `RUNNER_PROCESS_HANDLER=isolated` и штатно перезапустите runner после остановки его обработчиков.

Первое обращение после полного простоя группы по-прежнему требует загрузки Python и библиотек; мгновенный ответ не гарантируется. Пробуждение другого сценария, пока общий процесс ещё работает, может переиспользовать эти импорты, но чтение сценария, восстановление состояния, сетевые операции и сама обработка остаются. Конкретное ускорение и экономию следует подтверждать замерами: сравнивать весь процесс, пик при нескольких ботах и память после простоя, а не только среднее число мегабайт на бота. Сбой общего процесса затрагивает активные сценарии его группы; отдельные процессы обеспечивают более строгую изоляцию отказов и окружения.

### Число загруженных сценариев

Только сочетание `RUNNER_PROCESS_POLLING=node` и `RUNNER_PROCESS_HANDLER=shared` работает без фиксированного лимита загруженных ботов. Пятый и последующие боты не ждут засыпания первых четырёх: сохранённое обновление может пробудить их сценарий в том же общем Python. Это отсутствие ограничения по количеству, а не обещание бесконечной производительности: фактическую вместимость определяют память, CPU и внешние сервисы.

Сообщения каждого отдельного бота по-прежнему обрабатываются последовательно. Новый отдельный лимит параллельной обработки сообщений не вводится. Таймер выгрузки сценария `BOT_ON_DEMAND_IDLE_SECONDS` не меняется (по умолчанию 30 секунд); после выгрузки последнего сценария общий Python завершается, Node продолжает принимать обновления.

`BOT_ON_DEMAND_MAX_ACTIVE=0` означает отсутствие ограничения и используется по умолчанию. Значения от 1 до 64 задают явный предел для отдельных процессов `isolated` и прежнего Python-приёмника. Ноль не создаёт семафор без доступных мест. Сохранённые значения в БД и переменные окружения удалять или заменять специальным значением «безлимит» не требуется: общий Node/`shared`-путь их не применяет. При техническом откате на ограниченный путь сохранённый лимит снова действует. Счётчик максимума для неограниченного диспетчера передаётся как `null` и отображается как «Без фиксированного лимита», а не как нулевой доступный слот.

## Гарантии доставки и ограничения

- Приём начинается только после захвата общей с Python блокировки `bot:lock:*`. Она продлевается с проверкой владельца; потеря подтверждения останавливает приём и обработчик.
- Пакет и Telegram offset сохраняются одной атомарной операцией. Переполнение очереди или недоступный Redis запрещают подтверждение следующего offset.
- Схема очереди `tbb:demand:{TelegramBotId}:*` совпадает с Python. Не следует путать Telegram ID из токена с ID записи токена в БД.
- Python восстанавливает `user_data` до запуска сценария. Успешная обработка подтверждается атомарно с сохранением снимка состояния.
- Доставка допускает повтор после сбоя между внешним действием и подтверждением. Режим не предоставляет гарантию однократного выполнения внешних платежей или запросов.
- Несовместимая сборка с неподдерживаемыми фоновыми задачами должна быть отклонена; нельзя молча отключать её возможности.
- Токены и подключения передаются через закрытый stdin, не через аргументы процесса. Диагностический вывод очищается и ограничивается по размеру.
- Остановка и потеря аренды должны завершать дерево обработчика, включая Windows-лаунчер и фактический интерпретатор. Возврат управления до завершения дерева недопустим.

## Проверка перед использованием

Адресные тесты должны покрывать занятый и потерянный lease, Redis outage, переполнение очереди, восстановление offset и `user_data`, падение между сохранением и подтверждением, повторную доставку, отмену во время старта, остановку дочернего дерева и смесь legacy/Node-ботов. Снимки панели должны сохранять подтверждённые и ожидающие ID ботов, даже когда Python-процесс отсутствует. Проверка актуальности instance/generation перед запуском остаётся обязательной.

Тесты с подставным Telegram HTTP-сервером и отдельным префиксом Redis не должны отправлять сообщения настоящим пользователям. Полная локальная проверка типов правилами проекта запрещена; адресные тесты и сборка не заменяют диагностику типов.

## План сравнения памяти

### Лёгкие замеры задержек

Node-приёмник пишет в stdout runner события `polling_timing`: `received`, `persisted`,
`child_start`, `child_ready`, `handled`, `child_exit` и отказы транспорта/сохранения/запуска.
События содержат только время, ID бота и обновления, числовые длительности и коды.
Тексты сообщений, пользовательские ID, адреса и токены не записываются.
`telegramAgeMs` сравнивает время сообщения Telegram с часами сервера (точность Telegram — секунда).
`requestMs` включает нормальное ожидание long polling и само по себе не означает задержку ответа.
`startupMs` — запуск до готовности Python; `persistedToHandledMs` включает ожидание запуска,
очереди и обработку, а `handlerMs` берётся из штатного сообщения aiogram.
Для callback время исходного сообщения не используется как время нажатия.
Корреляция ограничена 1024 обновлениями; при переполнении старые отметки вытесняются,
очередь самих обновлений не затрагивается. После перезапуска старые отметки недоступны.
Это обычные лёгкие журналы, без V8 sampling и `tracemalloc`.

Внутри временного Python дополнительно публикуются этапы `python_*`: вход в процесс,
импорты инфраструктуры, подключение Redis, настройка aiogram, загрузка соседних модулей,
чтение байткода, выполнение модуля сценария, восстановление состояния и вход в `main()`.
`stageMs` — интервал с предыдущей отметки по монотонным часам Python,
`elapsedMs` — время от первой отметки. Интервал `main_begin` → `bot_ready`
пока объединяет внутренние операции и сетевые проверки самого сценария.
Разница между Node `child_start` и первой отметкой Python включает создание дерева
процессов и начальные импорты стандартной библиотеки до включения измерений.

1. Использовать одну сборку runner, одинаковые шесть ботов и неизменные Redis/БД, idle timeout и нагрузку. Отключить `tracemalloc`, V8 sampling и другие тяжёлые трассировщики.
2. Измерить базовый runner без ботов. Затем для `RUNNER_PROCESS_POLLING=python` запустить шесть ботов `process`, выдержать одинаковый прогрев и не менее двух idle timeout.
3. Записать отдельно RSS/PSS или Windows working set каждого Node/Python PID, число обработчиков, Node heap/external/arrayBuffers и память контейнера с разбиением anonymous/file. Не складывать файловые страницы повторно с RSS.
4. Подать одинаковый набор обновлений, проверить ответы и состояние сценария; записать пик, время первого ответа и память после завершения всех обработчиков.
5. Штатно перезапустить с `RUNNER_PROCESS_POLLING=node` и повторить те же этапы минимум трижды для `RUNNER_PROCESS_HANDLER=isolated` и `shared`. Проверить отсутствие Python до первого обновления и после полного простоя группы. Для `shared` отдельно проверить, что сон одного бота не завершает общий процесс, пока другой активен; измерить холодный ответ после полного простоя и ответ с переиспользованием уже работающего процесса.
6. Сравнить медиану общего расхода и прирост относительно базового runner, отдельно от среднего «весь runtime / число ботов». Зафиксировать цену переноса polling в Node, а не вычитать прежний Python RSS как гарантированную экономию.

Результаты должны включать время измерения, платформу, число ботов и активных обработчиков, значения переключателей, факт отключения диагностики и сценарий нагрузки. Цифры до фактического запуска нового пути не являются измерением его экономии.
