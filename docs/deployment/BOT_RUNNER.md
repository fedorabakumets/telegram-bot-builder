# Исполнитель ботов — `WORKER_RUNTIME=remote`

Исполнитель — отдельный процесс (`npm run runner`), который запускает Python-воркеры ботов на своей машине по командам панели. Панель при этом не запускает воркеры сама, а только управляет ими. Код бота исполнитель скачивает из [сборки в S3](BOT_BUILDS.md), поэтому общая папка `bots/` с панелью ему не нужна.

## Как включить

На панели:

```env
WORKER_RUNTIME=remote
WORKER_RUNNER_ID=runner-1
REDIS_URL=redis://...
# Код бота берётся из сборки в S3
BOT_ARTIFACT_SOURCE=storage
BOT_BUILDS_STORAGE_ID=<id S3-хранилища>
# Рекомендуется: переменные бота приходят в команде, а не из файла в папке бота
BOT_ENV_SOURCE=inline
# Необязательно: build (по умолчанию) — код из S3; path — путь к .py (общий диск)
WORKER_RUNNER_CODE=build
```

На исполнителе нужны только Redis и ID. Доступ к БД, S3 и секретам панели ему не нужен:

```env
REDIS_URL=redis://...   # тот же Redis, что у панели
RUNNER_ID=runner-1
# Необязательно:
RUNNER_PYTHON=python3
RUNNER_WORKER_SCRIPT=/path/to/server/python/worker.py
RUNNER_CACHE_DIR=~/.tbb-runner/builds   # кеш скачанных сборок
RUNNER_BUILDS_KEEP=20                   # сколько сборок хранить в кеше
```

```bash
npm run runner
```

Исполнитель читает `.env` из текущей папки. Python на его машине должен иметь зависимости ботов (`requirements.txt`).

## Как это работает

Протокол воркера не меняется: те же строки JSON, что раньше шли через stdin/stdout дочернего процесса. Только теперь они идут через Redis Streams:

| Поток | Кто пишет | Что внутри |
|---|---|---|
| `tbb:runner:<id>:cmd` | панель | `spawn` (поднять воркер), `line` (строка в stdin), `kill`, `reset` |
| `tbb:runner:<id>:ev` | исполнитель | `line` (строка stdout), `stderr`, `exit`, `error`, `hello` (исполнитель запущен) |

У каждого запуска воркера свой ID экземпляра, поэтому события старого воркера с тем же ключом не путаются с новым. Streams выбраны вместо pub/sub, потому что сообщения не теряются при коротком обрыве соединения.

- **Перезапуск панели.** При первом подключении панель отправляет `reset`, и исполнитель убивает воркеры, оставшиеся от прошлого запуска панели. Иначе их боты продолжили бы polling параллельно с новыми.
- **Перезапуск исполнителя.** При старте исполнитель отправляет `hello`, и панель сразу считает его прежние воркеры завершёнными. Иначе она ждала бы ответа от воркеров, которых уже нет. Если исполнитель убит через `kill -9`, его воркеры завершаются сами, когда закрывается stdin. Боты с включённым автоперезапуском поднимаются снова, остальных можно запустить вручную.
- **Остановка исполнителя (SIGINT/SIGTERM).** Исполнитель штатно останавливает воркеры, панель получает `exit` и отмечает ботов остановленными.
- **Память.** Воркер сам сообщает свою память (`WORKER_REPORT_MEMORY=true`), панель показывает её в статистике.
- **`${{VAR}}` в переменных бота.** Ссылка раскрывается только для имён из `WORKER_ENV_PASSTHROUGH`, как в режиме Docker. Так секреты панели не уходят на другую машину.

Код: `server/bots/workerChannel.ts` (канал до воркера), `remoteRunnerHub.ts`, `remoteWorkerChannel.ts`, `server/redis/workerStreams.ts`, `server/runner/`.

## Код бота из S3

При запуске панель сохраняет сборку в хранилище (как при `BOT_ARTIFACT_SOURCE=storage`) и кладёт в команду `start_bot` поле `build`: временную ссылку на файл в S3 (живёт 10 минут), `sha256`, размер, отпечаток сборки и имя файла. Ключей S3 у исполнителя нет, он скачивает файл только по этой ссылке.

Исполнитель:

1. Ищет сборку в кеше `RUNNER_CACHE_DIR/<отпечаток>/<файл>.py`. Если она есть, повторно не скачивает.
2. Иначе скачивает её, сверяет размер и `sha256` и только потом кладёт в кеш.
3. Подставляет путь к файлу в кеше в команду и передаёт её воркеру.
4. Чистит кеш до `RUNNER_BUILDS_KEEP` последних сборок, не трогая те, что сейчас запущены.

Если сборку скачать не удалось, бот получает запись в логе и статус ошибки запуска. Если сборки нет или хранилище не S3 (например, локальная папка `.bot-builds`), панель сразу отказывает в запуске с понятной ошибкой: локальное хранилище с другой машины недоступно.

Код: `server/bots/builds/botBuildLink.ts`, `runnerBuildForStart.ts`, `server/runner/runnerStartCommand.ts`, `runnerBuildCache.ts`.

## Исполнитель на Railway

Боты выбранных проектов можно запускать в отдельных сервисах Railway: панель сама создаёт сервис с исполнителем, разворачивает и останавливает его. См. [BOT_RAILWAY.md](BOT_RAILWAY.md).

## Ограничения

У режима пока есть ограничения:

- **Медиа.** Файлы из `/uploads` бот читает с локального диска, поэтому на другой машине медиа пока не отправляются. Их перенос в S3 — следующий шаг.
- **Секреты в Redis.** Переменные бота (с `BOT_ENV_SOURCE=inline`) лежат в потоке команд открытым текстом, пока запись не вытеснится (около 10 000 записей). Используйте закрытый Redis. Позже добавится шифрование для конкретного исполнителя.
- **Нет сигналов «жив».** Если исполнитель упал и не поднялся, панель этого не заметит: бот будет числиться запущенным, а его запуск завершится ошибкой по таймауту подтверждения. Если исполнитель поднялся снова, проблемы нет (см. `hello` выше).
- **Доступы бота.** Бот по-прежнему ходит в БД, Redis и API панели по адресам из своих переменных: они должны быть доступны с машины исполнителя.
