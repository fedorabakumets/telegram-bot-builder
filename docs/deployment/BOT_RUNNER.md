# Исполнитель ботов — `WORKER_RUNTIME=remote`

Исполнитель — отдельный процесс (`npm run runner`), который запускает Python-воркеры ботов на своей машине по командам панели. Панель при этом не запускает воркеры сама, а только управляет ими. Код бота исполнитель скачивает из [сборки в S3](BOT_BUILDS.md), поэтому общая папка `bots/` с панелью ему не нужна.

Рассылки исполняет API панели независимо от режима размещения ботов. Исполнитель не запускает очередь рассылок, аналитику или фоновые службы панели.

Общий сервис Telegram-аккаунтов может работать отдельно (`TELETHON_BROKER_MODE=external`, по умолчанию) или как дочерний процесс этого runtime (`embedded`). Встроенный брокер обслуживает все привязанные боты одним клиентом на аккаунт; он не является частью пространства Python-кода конкретного бота. Режим embedded допускает только один runtime-владелец и не поддерживает горизонтальное масштабирование одинаковыми репликами. Перед добавлением исполнителей выделите брокер обратно в отдельный сервис по [процедуре передачи владения](TELEGRAM_ACCOUNTS_RAILWAY.md). Runtime-хосту в embedded нужен секрет транспорта брокера, но сценарии ботов не получают этот секрет или строки сессий.

## Как включить

### Очередь запуска ботов

Все вызовы `startBot` проходят через одну очередь процесса API панели независимо от проекта и источника запуска: ручная кнопка, массовый запуск, перезапуск или восстановление. Одновременно выполняется не более **5 запусков во всех проектах суммарно**. Эти пять мест доступны и ботам одного проекта: отдельного ограничения «один запуск на проект» нет. Между началами допуска любых двух запусков выдерживается общий интервал не меньше **250 мс**; интервал отсчитывается от начала предыдущего допуска, а не от завершения запуска. Это предел одновременных стартовых операций, а не лимит количества работающих ботов.

Ограничение действует в одном процессе API панели; отдельные реплики API не делят его через Redis. Для текущего размещения с одной панелью очередь общая для всех её проектов. При добавлении реплик потребуется общий распределённый допуск, иначе каждая реплика получит собственные пять мест. Значения 5 и 250 мс заданы в коде, отдельных переменных окружения для них нет.

Допуск по памяти исполнителя сохраняется и проверяется после ожидания в очереди. Пять мест не означают, что исполнитель обязан запустить пять ботов одновременно: при нехватке памяти фактическая параллельность будет меньше. Устаревшая команда после ручной остановки или нового поколения не должна запускать бота при выходе из очереди. Уже работающие боты не перезапускаются ради освобождения стартового места.

### Допуск по памяти контейнера

Перед запуском нового shared/unified-сценария или isolated Python исполнитель читает
`memory.current` и конечный `memory.max` cgroup v2. Из доступного места вычитаются
резервы параллельных запусков, оценка стартового пика `RUNNER_MEMORY_START_MB`
(по умолчанию 64 МиБ) и запас `RUNNER_MEMORY_HEADROOM_MB` (64 МиБ по умолчанию,
но не меньше 15% лимита). Стартовый резерв удерживается до готовности и ещё
10 секунд, а после ошибки освобождается сразу. Все группы Node делят один резерв.
Если запуску мешает только временный резерв другого старта, исполнитель ждёт его
освобождения до 12 секунд и повторяет измерение каждые 250 мс. Ожидание не блокирует
очередь измерений. При нехватке памяти даже без временных резервов отказ немедленный;
лимит контейнера и защитный запас сохраняются.

При недостатке места новый запуск получает `memory_pressure`; уже работающие боты
не останавливаются. Боты с желаемым состоянием `running` автоматически ожидают места
в отдельной очереди сверки: максимум одна попытка за проход (по умолчанию каждые
5 секунд), минимум 5 секунд после завершения предыдущей попытки. Перед запуском
исполнитель повторно проверяет память; отказ оставляет бота ждать. Очередь обходит
ботов по кругу, чтобы один отказ не блокировал остальных. Ручной стоп, смена
поколения, отзыв токена и заморозка отменяют устаревшее ожидание. Это не аварийный
цикл автоперезапуска и он не расходует его лимит попыток. После рестарта панели
ожидание восстанавливается из сохранённых намерений и причины `runner_memory`.
На системах без доступного
конечного лимита cgroup прежнее поведение сохраняется; нули и некорректные env-значения
не отключают запас. Эти настройки задаются в окружении самого исполнителя.

Это защита стартовых пиков, а не жёсткая квота каждого бота: последующий рост данных
и сторонние процессы всё ещё могут исчерпать контейнер. Лимит 500 МБ не гарантирует
вместимость 31 бота; следует измерять пиковую память реальных сценариев и выбирать
ёмкость исполнителя. Изменение этих настроек не повышает лимит Railway автоматически.

Те же поля задаются в админке, раздел «Исполнители» ([настройки рантайма](../interface/admin-settings.md)). Пока значение не сохранено, читается переменная окружения. Секрет Redis в `process.env` воркера не копируется.

На панели:

```env
WORKER_RUNTIME=remote
WORKER_RUNNER_ID=runner-1
REDIS_URL=redis://...
# Код бота берётся из сборки в S3
BOT_ARTIFACT_SOURCE=storage
BOT_BUILDS_STORAGE_ID=<id S3-хранилища>
# Рекомендуется: переменные бота приходят в команде, а не из файла в папке бота
BOT_ENV_SOURCE=inline
# Необязательно: build (по умолчанию) — код из S3; path — путь к .py (общий диск)
WORKER_RUNNER_CODE=build
```

Для транспорта исполнителю нужны Redis и ID; ключи S3 ему не нужны. При включённой защите актуальности команд (`RUNNER_REQUIRE_FENCE=true`, включено в `dev:runtime` и `start:runtime`) дополнительно нужен `DATABASE_URL`: небольшой ленивый пул проверяет только версию команды в `bot_instances`. Общий пул и службы БД панели не загружаются.

```env
REDIS_URL=redis://...   # тот же Redis, что у панели
RUNNER_ID=runner-1
RUNNER_REQUIRE_FENCE=true
DATABASE_URL=postgresql://...   # для проверки актуальности команд бота
# Необязательно:
RUNNER_PYTHON=python3
RUNNER_WORKER_SCRIPT=/path/to/server/python/worker.py
RUNNER_CACHE_DIR=~/.tbb-runner/builds   # кеш скачанных сборок
RUNNER_BUILDS_KEEP=20                   # сколько сборок хранить в кеше
```

```bash
npm run runner
```

Исполнитель читает `.env` из текущей папки. Python на его машине должен иметь зависимости ботов (`requirements.txt`).

## Как это работает

Протокол воркера не меняется: те же строки JSON, что раньше шли через stdin/stdout дочернего процесса. Только теперь они идут через Redis Streams:

| Поток | Кто пишет | Что внутри |
|---|---|---|
| `tbb:runner:<id>:cmd` | панель | `spawn` (поднять воркер), `line` (строка в stdin), `kill`, `reset` |
| `tbb:runner:<id>:ev` | исполнитель | `line` (строка stdout), `stderr`, `exit`, `error`, `hello` (исполнитель запущен) |

У каждого запуска воркера свой ID экземпляра, поэтому события старого воркера с тем же ключом не путаются с новым. Streams выбраны вместо pub/sub, потому что сообщения не теряются при коротком обрыве соединения.

- **Перезапуск панели.** При первом подключении панель отправляет `reset`, и исполнитель убивает воркеры, оставшиеся от прошлого запуска панели. Иначе их боты продолжили бы polling параллельно с новыми.
- **Перезапуск исполнителя.** При старте исполнитель отправляет `hello`, и панель сразу считает его прежние воркеры завершёнными. Иначе она ждала бы ответа от воркеров, которых уже нет. Если исполнитель убит через `kill -9`, его воркеры завершаются сами, когда закрывается stdin. Боты с включённым автоперезапуском поднимаются снова, остальных можно запустить вручную.
- **Остановка исполнителя (SIGINT/SIGTERM).** Исполнитель штатно останавливает воркеры, панель получает `exit` и отмечает ботов остановленными.
- **Память.** Воркер сам сообщает свою память (`WORKER_REPORT_MEMORY=true`), панель показывает её в статистике.
- **`${{VAR}}` в переменных бота.** Ссылка раскрывается только для имён из `WORKER_ENV_PASSTHROUGH` панели вне denylist, как во всех режимах (см. [WORKER_DOCKER.md](./WORKER_DOCKER.md#серверные-переменные-и-боты-все-режимы)). Так секреты панели не уходят на другую машину.
- **Окружение воркера на исполнителе.** worker.py не наследует окружение исполнителя: только технические переменные (PATH, локаль, PYTHON*) и `WORKER_ENV_PASSTHROUGH` исполнителя вне denylist. `REDIS_URL` исполнителя (канал к панели) боту не передаётся — подключения бот получает в команде `start_bot`.

Код: `server/bots/workerChannel.ts` (канал до воркера), `remoteRunnerHub.ts`, `remoteWorkerChannel.ts`, `server/redis/workerStreams.ts`, `server/runner/`.

## Код бота из S3

При запуске панель сохраняет сборку в хранилище (как при `BOT_ARTIFACT_SOURCE=storage`) и кладёт в команду `start_bot` поле `build`: временную ссылку на файл в S3 (живёт 10 минут), `sha256`, размер, отпечаток сборки и имя файла. Ключей S3 у исполнителя нет, он скачивает файл только по этой ссылке.

Исполнитель:

1. Ищет сборку в кеше `RUNNER_CACHE_DIR/<отпечаток>/<файл>.py`. Если она есть, повторно не скачивает.
2. Иначе скачивает её, сверяет размер и `sha256` и только потом кладёт в кеш.
3. Подставляет путь к файлу в кеше в команду и передаёт её воркеру.
4. Чистит кеш до `RUNNER_BUILDS_KEEP` последних сборок, не трогая те, что сейчас запущены.

Если сборку скачать не удалось, бот получает запись в логе и статус ошибки запуска. Если сборки нет или хранилище не S3 (например, локальная папка `.bot-builds`), панель сразу отказывает в запуске с понятной ошибкой: локальное хранилище с другой машины недоступно.

Код: `server/bots/builds/botBuildLink.ts`, `runnerBuildForStart.ts`, `server/runner/runnerStartCommand.ts`, `runnerBuildCache.ts`.

## Исполнитель на Railway

Боты выбранных проектов можно запускать в отдельных сервисах Railway: панель сама создаёт сервис с исполнителем, разворачивает и останавливает его. См. [BOT_RAILWAY.md](BOT_RAILWAY.md).

## Ограничения

У режима пока есть ограничения:

- **Медиа.** Файлы из `/uploads` бот читает с локального диска, поэтому на другой машине медиа пока не отправляются. Их перенос в S3 — следующий шаг.
- **Секреты в Redis.** Переменные бота (с `BOT_ENV_SOURCE=inline`) лежат в потоке команд открытым текстом, пока запись не вытеснится (около 10 000 записей). Используйте закрытый Redis. Позже добавится шифрование для конкретного исполнителя.
- **Нет сигналов «жив».** Если исполнитель упал и не поднялся, панель этого не заметит: бот будет числиться запущенным, а его запуск завершится ошибкой по таймауту подтверждения. Если исполнитель поднялся снова, проблемы нет (см. `hello` выше).
- **Доступы бота.** Бот по-прежнему ходит в БД, Redis и API панели по адресам из своих переменных: они должны быть доступны с машины исполнителя.
