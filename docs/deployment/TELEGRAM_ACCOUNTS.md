# Общие Telegram-аккаунты

Перед выпуском проверьте функцию на отдельном окружении с тестовым проектом, двумя тестовыми ботами и выделенным Telegram-аккаунтом. Для карточек и общего клиента подходит [раздельный запуск](SPLIT_RUNTIME_LOCAL.md). Перенос проверяйте отдельно для каждого поддерживаемого способа запуска. Для проверки сбоев используйте синтетические данные и подменённый транспорт Telegram.

## Подготовка

### Единственный владелец Telegram-сессий

До распределения аккаунтов по владельцам допускается только **один брокер для всего окружения**. Помимо локального lock-файла брокер использует общий `REDIS_URL` и постоянный ключ `tbb:telethon-broker:singleton:v1`. Все экземпляры должны использовать один Redis и одну его базу. Брокер не создаёт отсутствующий ключ и не перехватывает занятый ключ. Нет TTL и автоматического failover: сетевой сбой не даёт второму процессу права открыть те же сессии.

Первичная подготовка выполняется администратором **только когда все брокеры остановлены**: в подключении Redis выбранного окружения выполнить `SET tbb:telethon-broker:singleton:v1 unowned NX`. Затем можно запустить один брокер. Не добавляйте эту команду в автоматический запуск. При отсутствии ключа (включая потерю данных Redis) startup завершается до создания Telethon-клиентов.

При штатной остановке брокер сначала закрывает все клиенты и лишь затем возвращает значение `unowned`. Локальный dev-launcher может передать `shutdown` в stdin при `TELETHON_BROKER_STDIN_CONTROL=1`, чтобы на Windows также выполнялся cleanup. Принудительное завершение, ошибка отключения или потеря Redis оставляют окружение заблокированным. Брокер проверяет владение перед запросами и в фоне; при сбое запрещает новые операции и закрывает клиентов, не возобновляясь автоматически.

Аварийное восстановление: остановить и подтвердить завершение **всех** прежних брокеров на всех хостах, проверить отсутствие процессов с этой сессией, восстановить доступность Redis и только затем вручную выполнить `SET tbb:telethon-broker:singleton:v1 unowned`. После этого запустить ровно один брокер. Не сбрасывайте занятый ключ при живом процессе: Telegram не поддерживает fencing внешнего клиента, поэтому ручное снятие защиты может создать дубликат. Самостоятельно работающие старые скрипты и другие базы Redis не входят в эту гарантию.

- Примените миграции на стенде командой `npm run migrate` с его `DATABASE_URL`. Перед выпуском проверьте миграцию `0048_project_telegram_accounts.sql` на копии совместимой схемы.
- API использует постоянный `STORAGE_ENCRYPTION_KEY` для шифрования сессий и паролей прокси. Сохраните этот ключ вместе с процедурой восстановления базы. Замена ключа без переноса данных оставит прежние сессии нечитаемыми.
- В раздельном режиме `PROJECT_TELEGRAM_API_BASE` указывает на API, доступный исполнителю. В Compose это `http://api:5000`, при запуске процессов `dev:api` и `dev:runtime` на одной машине это `http://127.0.0.1:5001`. `PROJECT_TELEGRAM_RUNNER_SECRET` хранится на API и подписывает ключи отдельных ботов.
- По умолчанию брокер слушает loopback, и API находится с ним в одном сетевом пространстве: `TELETHON_BROKER_URL=http://127.0.0.1:8765`. Для отдельного сервиса в частной сети требуется явный `TELETHON_BROKER_ALLOW_PRIVATE_NETWORK=1` и сетевой bind. Запускайте один брокер для окружения и используйте постоянный том для `TELETHON_BROKER_LOCK_FILE`. API и брокер используют одинаковый `TELETHON_BROKER_SECRET`; секрет подписи раннера независим. Оба секрета имеют длину не менее 32 байт.
- Включайте `PROJECT_TELEGRAM_ACCOUNTS_ENABLED=1` после запуска брокера и применения миграций. До включения действуют персональные сессии.

Для локального запуска API, исполнителя и брокера используйте оба профиля Compose:

```sh
docker compose --profile split --profile telegram-accounts up --build db redis api runtime frontend telegram-accounts
```

В Compose сервис `telegram-accounts` использует сетевое пространство API и не публикует порт. Исполнитель связывается только с API. Для отдельного брокера Railway используйте частную сеть, постоянный том и явное разрешение сетевого bind по [инструкции выпуска](TELEGRAM_ACCOUNTS_RAILWAY.md). Loopback-адрес другого контейнера недоступен через частное имя; наличие конфигов в репозитории не означает выполненный деплой.

## Автоматические локальные проверки

```sh
npx --no-install vitest run --project lib lib/tests/project-telegram-accounts-http.test.ts
npx --no-install vitest run --project lib lib/tests/project-telegram-accounts-postgres.test.ts
```

Первая команда запускает loopback API с подменённым хранилищем и брокером. Вторая использует изолированную временную схему PostgreSQL и пропускается без `TELEGRAM_ACCOUNTS_TEST_DATABASE_URL`. Укажите в этой переменной адрес локальной тестовой базы с правом создания схем. После проверки временная схема удаляется.

## Приёмка на стенде

1. Создайте два проекта и откройте «Боты → Аккаунты». Создайте аккаунт в первом проекте, обновите страницу и убедитесь, что он сохранён. Запрос аккаунта из второго проекта и попытка привязать его бота должны отклоняться.
2. Если нужен прокси, сохраните его перед авторизацией. Авторизуйте тестовый аккаунт и привяжите к нему двух ботов первого проекта. Проверьте привязку из карточки аккаунта и настроек каждого бота. Перенос одного бота на другой аккаунт должен сохранять привязку второго.
3. Проверьте действия обоих ботов на выделенном тестовом чате. Для каждой действующей сессии один клиент обслуживает запросы от обоих ботов. Перезапуск или остановка одного бота должны сохранять работоспособность второго.
4. Проверьте неверный код, неподходящий файл импорта и прокси с приватным адресом. Ошибка должна быть понятна из интерфейса и сохранять ранее проверенную сессию. Кнопка проверки прокси валидирует публичный адрес. Чтобы подтвердить передачу трафика, выполните тестовое действие через брокер с прокси и отдельно проверьте отказ при недоступном прокси и брокере.
5. Проверьте ответы API и логи на синтетических секретах. Строка сессии, хеш API, код подтверждения, пароль и данные прокси должны отсутствовать в ответах интерфейса, событиях и диагностических сообщениях.
6. Убедитесь, что существующий бот с персональной сессией работает до явной смены привязки и после снятия новой привязки согласно правилам проекта.

## Перенос существующих ботов

Начните с предварительного просмотра. Проверьте состав группы. Автоматический перенос создаёт новую карточку для группы, помеченной как «Создать аккаунт».

На отдельном стенде включите `PROJECT_TELEGRAM_ACCOUNT_CUTOVER_ENABLED=1` и пул воркеров. Оставьте `WORKER_RAILWAY_PROJECTS` пустой. Брокер остаётся отдельным сервисом с постоянным томом.

- **Локальный процесс.** Запустите панель через `npm run dev` с `BOT_RUNTIME_MODE=combined` и `WORKER_RUNTIME=process`. Перенос ждёт события выхода дочернего процесса. Если бот уже остановлен, панель принимает только ранее полученное в этом процессе подтверждение выхода выделенного воркера без новой попытки запуска. Запись в БД о статусе бота сама по себе этого не доказывает.
- **Docker.** В совмещённом режиме установите `WORKER_RUNTIME=docker`. Перенос проверяет выход конкретного контейнера по ID, полученному при запуске. Завершение Docker CLI или отсутствие контейнера с данным именем не считаются доказательством.
- **Отдельный исполнитель.** Используйте `BOT_RUNTIME_MODE=api`, `WORKER_RUNTIME=remote` и общий Redis. Включите `RUNNER_REQUIRE_FENCE=true` на исполнителе. До остановки обновляются версии команд, а завершение подтверждает исполнитель для того же экземпляра воркера.

При любой группировке перенос целого воркера возможен только тогда, когда в нём нет других активных или запускающихся ботов. При недостаточном подтверждении состояние сохраняется в журнале, а общий клиент не запускается.

Операции переноса доступны владельцу под общим путём `/api/projects/:projectId/telegram-accounts`:

- `GET /migration/preview` возвращает группы и причины исключений.
- `GET /migration/operations` возвращает ранее сохранённые операции и доступность нового переноса.
- `POST /migration/apply` принимает `migrationId` и `groupId` из выбранной группы.
- `POST /migration/rollback` принимает тот же `migrationId`.

Статус «Подключён» означает, что авторизация подтверждалась. Работу общего клиента в конкретный момент подтвердите отдельным вызовом от привязанного бота.

Для возобновления переноса используйте тот же идентификатор операции и тот же набор ботов. Журнал отражает подтверждённые действия `prepared` → `legacy-stopped` → `shared-installed` → `shared-ready`. Если остановка старых клиентов не подтверждена, остаётся `prepared`.

При откате дождитесь подтверждения отключения общего клиента. Только после этого восстанавливаются старые привязки и исходное состояние запусков. Если старые боты пользовались одним и тем же ключом, одновременно запускать их нельзя. При отсутствии подтверждения отключения журнал остаётся в `rollback-started`. Достигнутая фаза успешного отката — `rolled-back`. Для нового переноса после завершённого отката используйте новый идентификатор операции и новую карточку. Отключение переключателя функции и ручной запуск старых ботов во время переноса могут повторно открыть соединение с тем же ключом.

До остановки ботов API проверяет сценарий. Вложения Userbot, рассылки Client API с медиа и прямые обращения к клиенту из узлов кода требуют отдельного клиента. Подписки на новые сообщения и редактирование обслуживаются журналом событий общего брокера с ограничениями доставки, описанными в инструкции Railway. Текстовая рассылка Client API использует общий клиент.

## Действия при сбое

- Если подключение аккаунта пропало у всех привязанных ботов, проверьте здоровье общего клиента и доступность Telegram через заданный прокси. Повторную авторизацию выполняйте для самого аккаунта.
- При потере доступа к сессии завершите соответствующую сессию в Telegram и подключите аккаунт заново. Если секрет попал в лог, ограничьте доступ к записи и обработайте инцидент по правилам проекта.
- Если новая версия нарушает работу существующих ботов, приостановите выпуск. До отката приложения проверьте совместимость со схемой данных. Восстановление базы выполняется по [инструкции резервного копирования](DB_BACKUPS.md).
