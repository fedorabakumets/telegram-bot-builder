# Выделение исполнителя ботов

## Границы сервисов

Одна кодовая база собирается в три приложения: frontend, API и bot runtime. PostgreSQL и Redis остаются общими. Совместный режим сохраняет привычный локальный запуск. Отдельный API включается только явной настройкой `BOT_RUNTIME_MODE=api` вместе с `WORKER_RUNTIME=remote`.

В текущей подготовительной версии режим `api` не допускает `WORKER_RAILWAY_PROJECTS`: это отдельная схема размещения исполнителей, для которой нужна своя интеграционная проверка.

API владеет авторизацией, проектами, сборкой кода, записями о желаемом состоянии и пользовательскими запросами запуска или остановки. Runtime владеет Python-процессами и фактом выполнения. Запись `desired_status=running` означает намерение, а не доказательство, что бот уже работает.

## Сверка состояния

При подключении API запрашивает у исполнителя снимок активных и готовящихся ботов. Активные воркеры привязываются к новому процессу API без перезапуска Python. После открытия HTTP-порта API сверяет снимок с `bot_instances.desired_status`: пропущенный запуск повторяется с новой ссылкой на сборку, пропущенная остановка выполняется. Сверка повторяется периодически. Если исполнитель не отвечает, состояние считается неизвестным; API не должен заявлять, что бот остановлен.

Новая команда пользователя увеличивает `desired_generation`. Проход сверки перечитывает поколение перед действием, чтобы пропускать устаревшее намерение. Снимок включает ботов, для которых команда запуска уже принята, но подготовка сборки ещё не завершена: их нельзя запускать повторно. Если временная ссылка на сборку истекла, исполнитель сообщает отдельный признак ошибки. API может создать новую ссылку и повторить запуск не более двух раз на поколение намерения; счётчик и пауза между попытками хранятся в БД. Остальные ошибки запуска не запускают бесконечную сверку.

Один `runnerId` арендуется одним процессом через Redis. При потере аренды runtime немедленно убивает Python-воркеры. Перед пересылкой команды в Python runtime может проверить `instance_id` и `desired_generation` по PostgreSQL. Для этого ему требуется доступ к БД и `RUNNER_REQUIRE_FENCE=true`; без этой настройки старый протокол команд по-прежнему допускается.

## Критерии перед production

- Проверить на двух процессах повтор неподтверждённых команд после обрыва Redis и перезапуска runtime. Команда подтверждается после передачи Python-воркеру, поэтому `bot_started` остаётся отдельным подтверждением фактической работы.
- Проверить, что все пути запуска и остановки передают поколение намерения, а runtime с `RUNNER_REQUIRE_FENCE=true` отвергает устаревшую команду запуска после нового запроса остановки.
- Зависшая подготовка сборки должна иметь обнаруживаемое состояние и безопасное восстановление без второго экземпляра бота.
- Проверить остановку и восстановление расписаний, рассылок, медиа, сборок и статусов на двух отдельных процессах.
- Выполнить целевые проверки и сценарий отката на тестовой среде.

Команды runtime теперь читает через Redis consumer group, подтверждает `XACK` после обработки и удаляет подтверждённую запись. Поток команд не обрезается по длине, чтобы не терять ожидающие записи. События для API по-прежнему читаются с хвоста; после рестарта API фактическое состояние восстанавливается через снимок исполнителя. До выполнения критериев отдельный режим следует считать подготовительным. Настройки Railway и production меняются только отдельным решением после проверки текущего состояния.
