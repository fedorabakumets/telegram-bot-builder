# Раздельный запуск одной кодовой базы

Обычный `npm run dev` запускает совмещённую панель на порту 5000. Существующий `npm run dev:split` запускает API и frontend двумя процессами. Для проверки трёх сервисов запустите в отдельных терминалах `npm run dev:api`, `npm run dev:runtime` и `npm run dev:frontend`. В трёхсервисном режиме frontend слушает порт 5000, API — 5001, а runtime принимает команды через Redis без HTTP-порта. Укажите одинаковый `REDIS_URL` для API и runtime; `WORKER_RUNNER_ID` API должен совпадать с `RUNNER_ID` исполнителя (по умолчанию `default`). Рассылки исполняются внутри API как в совмещённом, так и в раздельном режиме. Runtime занимается только процессами ботов и проверкой актуальности команд. `dev:api` задаёт `BOT_RUNTIME_MODE=api`; `dev:runtime` и Compose включают `RUNNER_REQUIRE_FENCE=true`. Для этой проверки runtime нужен `DATABASE_URL`, но общий слой БД панели и её фоновые службы не загружаются.

Когда API и runtime работают на одном компьютере, задайте в локальном `.env` `MEDIA_RUNTIME_BASE_URL=http://127.0.0.1:5001`, `MEDIA_RUNTIME_ALLOW_INSECURE_REMOTE=true` и `MEDIA_RUNTIME_ALLOW_LOCAL_LOOPBACK=true`. Для медиа нужен постоянный `MEDIA_RUNTIME_SECRET` длиной не менее 32 символов. Разрешение loopback действует только при `NODE_ENV=development` и не распространяется на проекты с отдельным Railway-исполнителем. В обычном `npm run dev` эти переменные не нужны.

Команды сборки: `npm run build:frontend`, `npm run build:api`, `npm run build:runtime`. Общая `npm run build` сохраняет прежнее поведение. Образы независимо собираются из `Dockerfile.frontend`, `Dockerfile.backend` и `Dockerfile.runner`. Подготовленные конфиги `railway.frontend.toml`, `railway.backend.toml` и `railway.runtime.toml` можно назначить сервисам при отдельном переключении; их наличие в репозитории ничего не развёртывает.

В Compose обычный `docker compose up --build` сохраняет совмещённый сервис `app`. Для раздельного профиля используйте `docker compose --profile split up --build db redis api runtime frontend`. Для реального запуска ботов в этом профиле задайте S3-совместимое хранилище и `BOT_BUILDS_STORAGE_ID`: исполнитель скачивает сборку по подписанной ссылке, а общую папку с API не использует. Перед настройкой хранилища изучите [хранение сборок](BOT_BUILDS.md).

Этот профиль предназначен для локальной проверки. Конфигурацию действующих сервисов Railway он не меняет.

## Соединения PostgreSQL

Общий пул API допускает до 10 соединений, ждёт выдачи до 20 секунд и закрывает свободные соединения после 30 секунд простоя с учётом минимального размера пула. Исполнитель создаёт отдельный пул только при проверке команды бота: до 2 соединений с закрытием после 10 секунд простоя, без фонового опроса БД. Обработчики пользователей бота используют общий пул API. Подписка аналитики работает через отдельное соединение, поэтому предельное число для API — 10 соединений пула плюс одно соединение подписки.

В `pg_stat_activity.application_name` основной API обозначен `botcraft-api`, проверка команд исполнителя — `botcraft-runtime-command-fence`, подписка — `botcraft-api-analytics-listener`. Переменная `PGAPPNAME` позволяет переопределить базовое имя. При явном `application_name` в строке подключения учитывайте приоритет настроек драйвера PostgreSQL.

Диагностика `[database-pool]` сообщает о таймаутах выдачи и удержании клиента более 30 секунд: количество открытых, свободных, выданных и ожидающих соединений, а для долгого удержания — место выдачи в коде. SQL и параметры подключения в эти события не включаются. Намеренное удержание соединения рассылкой исключено из предупреждений; каждая активная рассылка занимает одно соединение для сессионной блокировки, одновременно выполняется не более трёх рассылок.

При пустой очереди рассылок пауза проверок увеличивается до 10 секунд; фоновая обработка снимков и удаления файлов замедляется до 30 секунд. Обнаружение нового задания может занять эту паузу плюс время запроса. При наличии работы пауза возвращается к 2 секундам, а проходы планировщиков не накладываются.
