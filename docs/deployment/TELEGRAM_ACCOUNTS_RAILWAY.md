# Общие Telegram-аккаунты на Railway

Это инструкция контролируемого выпуска, а не подтверждение выполненного деплоя. Конфиги в репозитории не создают сервисы и не переносят действующие сессии автоматически. Общие правила владения, миграции аккаунтов и восстановления описаны в [TELEGRAM_ACCOUNTS.md](TELEGRAM_ACCOUNTS.md).

## Сервисы и переменные

Для раздельного размещения нужны frontend, backend API и runtime, а также PostgreSQL, Redis и хранилище сборок. В топологии `standalone` добавляется один сервис `telegram-accounts`; в `embedded` тот же брокер запускается внутри единственного runtime. Все компоненты одного окружения используют согласованные подключения к базе и Redis. Брокер открывает единственный Telethon-клиент аккаунта; сценарий бота обращается к API и не получает строку сессии.
Для отдельного брокера используйте `Dockerfile.telegram-accounts` и его штатный `CMD`: не заменяйте его Railway `startCommand`, иначе подготовка прав тома и обработка сигналов могут быть обойдены. В standalone IaC задаёт одну реплику, нулевое перекрытие и 75 секунд штатного завершения; эти настройки не заменяют проверку выхода прежнего владельца. Embedded использует образ `Dockerfile.runner` и 120 секунд завершения runtime.

| Сервис | Настройки |
|---|---|
| Backend API | `APP_MODE=backend`, `BOT_RUNTIME_MODE=api`, `WORKER_RUNTIME=remote`; `DATABASE_URL`, `REDIS_URL`; `WORKER_RUNNER_ID` совпадает с `RUNNER_ID` runtime |
| Backend API | `PROJECT_TELEGRAM_ACCOUNTS_ENABLED=0` до завершения подготовки; `PROJECT_TELEGRAM_API_BASE` — внутренний адрес **backend**, доступный runtime, в IaC — ссылка на `bot builder backend.RAILWAY_PRIVATE_DOMAIN` и его `PORT` |
| Backend API | `TELETHON_BROKER_URL` — внутренний адрес брокера, например `http://telegram-accounts.railway.internal:8765`; `TELETHON_BROKER_SECRET` совпадает с секретом брокера |
| Backend API | Постоянные `STORAGE_ENCRYPTION_KEY` и отдельный `PROJECT_TELEGRAM_RUNNER_SECRET`; последний не передаётся целиком в runtime |
| Runtime | `RUNNER_ID`, `RUNNER_REQUIRE_FENCE=true`, `DATABASE_URL`, `REDIS_URL`; настройки сборок и памяти — по [BOT_RUNNER.md](BOT_RUNNER.md) |
| Telegram accounts | `TELETHON_BROKER_ALLOW_PRIVATE_NETWORK=1`, `TELETHON_BROKER_HOST=::`, `TELETHON_BROKER_PORT=8765`, `TELETHON_BROKER_SECRET`, общий `REDIS_URL` |
| Telegram accounts | Постоянный том `/var/lib/botcraft-telegram`; `TELETHON_BROKER_LOCK_FILE=/var/lib/botcraft-telegram/broker.lock`; ровно одна реплика |

В текущем IaC сервис API называется `bot builder backend`. Он сохраняет действующий `TELETHON_BROKER_SECRET` через `preserve()`; новый брокер ссылается на секрет API, а не наоборот. Перед первым планом создайте отсутствующие секреты на API; флаги также сохраняются через `preserve()`, поэтому на новом окружении явно задайте их равными `0`, а на действующем не сбрасывайте их без процедуры переноса.

Примеры Railway reference variables для текущих имён сервисов в standalone; embedded-адрес приведён в таблице ниже:

```text
# На API:
TELETHON_BROKER_URL=http://${{telegram-accounts.RAILWAY_PRIVATE_DOMAIN}}:8765
PROJECT_TELEGRAM_API_BASE=http://${{bot builder backend.RAILWAY_PRIVATE_DOMAIN}}:${{bot builder backend.PORT}}
# На брокере:
TELETHON_BROKER_SECRET=${{bot builder backend.TELETHON_BROKER_SECRET}}
REDIS_URL=${{Redis.REDIS_URL}}
```

Имена сервисов и порт backend нужно сверить с конкретным окружением. Секреты задаются в Railway, не в Git; секрет брокера и секрет подписи runtime независимы и имеют длину не менее 32 байт. Не создавайте публичный домен или TCP proxy брокера. Флаг private network разрешает bind на сетевой интерфейс, но сам по себе не ограничивает доступ инфраструктуры. `/v1/*` требует секрет даже в частной сети.

## Выбор standalone или embedded

IaC выбирает топологию константой `TELEGRAM_BROKER_TOPOLOGY` в `.railway/telegram-broker-topology.ts`; значение по умолчанию — `standalone`. Это изменение желаемого графа сервисов, а не динамическое переключение живых клиентов. Применять план разрешается только после передачи владения, описанной ниже. Наличие кода не подтверждает, что выбранная топология уже развёрнута.

В embedded IaC задаёт runtime `PORT=8765` и healthcheck `/healthz` с таймаутом 120 секунд: готовность требует подтверждённого Redis-владения брокера. Webhook продолжает слушать отдельный `RUNNER_WEBHOOK_PORT=9080`. Закрытие брокера получает до 70 секунд на штатный cleanup; после принудительного завершения успешное закрытие сессий не подтверждается и автоматического захвата владения нет.

| Размещение | Standalone | Embedded |
|---|---|---|
| Процесс брокера | Сервис `telegram-accounts` | Дочерний процесс `bot runtime` |
| `TELETHON_BROKER_MODE` runtime | `external` | `embedded` |
| URL брокера на API | `http://${{telegram-accounts.RAILWAY_PRIVATE_DOMAIN}}:8765` | `http://${{bot runtime.RAILWAY_PRIVATE_DOMAIN}}:8765` |
| Секрет брокера | Ссылка на секрет backend в отдельном сервисе | Та же ссылка в окружении runtime-хоста |
| Том `telegram-accounts-volume` | Подключён к брокеру | Перенесён к runtime по тому же пути `/var/lib/botcraft-telegram` |
| Число владельцев | Один отдельный брокер | Один runtime, один дочерний брокер |
| Штатное завершение IaC | 75 секунд брокеру, без перекрытия | 120 секунд runtime и его брокеру, без перекрытия |

Обычный `external` не запускает брокер в runtime и не требует там секрет брокера или его том. В embedded он нужен родительскому процессу для запуска дочернего брокера; переменные транспорта и session credentials не должны попадать в окружение Python-сценариев. `PROJECT_TELEGRAM_API_BASE` в обоих режимах по-прежнему указывает на backend, не на порт брокера. API хранит ключ шифрования и читает сессии, а runtime-host не получает его ради embedded.
Runtime ждёт маркер `TELETHON_BROKER_READY`, который выдаётся после захвата singleton и привязки сокета. При ошибке запуска он не принимает обычные команды ботов; неожиданное завершение встроенного брокера завершает владельца вместо автоматического запуска второго клиента. `/healthz` остаётся проверкой самого брокера на порту 8765; readiness отдельного HTTP-приёмника runtime не заменяет её.

Embedded допустим для одного экземпляра runtime. Не увеличивайте его реплики и не запускайте одновременно внешний брокер: постоянный singleton отклонит нового владельца; это защита от дубликатов, а не механизм распределения аккаунтов. При росте нагрузки сначала вернитесь к отдельному брокеру. Даже standalone пока имеет одного владельца всего окружения, а не распределённые шарды аккаунтов.

### Передача standalone ↔ embedded

1. Остановите приём новых операций и потребителей аккаунтов, включая фоновые подписки и сценарии всех привязанных ботов. Остановите прежнего владельца брокера и подтвердите завершение его процесса и закрытие клиентов. Для embedded это также остановка его runtime; для standalone — отдельного сервиса. Dev-копии того же auth key тоже должны быть остановлены.
2. Проверьте журнал штатного завершения и состояние постоянного singleton. После подтверждённого cleanup он возвращается в `unowned`. Если процесс упал или закрытие не подтверждено, автоматического захвата не будет: используйте ручную процедуру восстановления только после доказанной остановки всех прежних владельцев.
3. Измените топологию в Git и проверьте IaC plan. План должен убрать прежний сервис-владелец либо его embedded-настройки и перенести **тот же** том `telegram-accounts-volume` новому владельцу. Не подключайте том двум владельцам одновременно; не заменяйте его новым пустым томом, иначе потеряется сохранённая блокировка аккаунтов. Удаление сервиса и перенос тома — контролируемые инфраструктурные действия, не обычный rolling restart.
4. Примените проверенный план в окно обслуживания, запустите только нового владельца и дождитесь `/healthz` на его порту 8765. Убедитесь, что backend использует новый private URL, а runtime — правильный режим. Старый адрес и старый процесс не должны продолжать обслуживать сессии.
5. Проверьте синтетическую цепочку runtime → API → broker и лишь затем возобновляйте потребителей. После передачи буфер событий не переносится: подписки создают новый курсор и должны учитывать разрыв доставки. Обратный переход выполняется теми же шагами.

## Готовность и выпуск

1. Сделайте резервную копию БД и сохраните действующий ключ шифрования. Примените `npm run migrate` с целевым `DATABASE_URL`, включая `0048_project_telegram_accounts.sql`. Выключенный флаг функции не заменяет миграции.
2. До открытия той же сессии на Railway остановите dev-брокер, старые standalone-боты и другие процессы с этим ключом. Подтвердите их завершение. Разные окружения Redis не защищают друг от друга: нельзя одновременно держать копию одной StringSession в dev и production.
3. Подготовьте один Redis выбранного окружения с сохранением данных. Только при подтверждённой остановке всех прежних владельцев выполните `SET tbb:telethon-broker:singleton:v1 unowned NX`. Автоматический старт не должен выполнять инициализацию или сброс ключа.
4. Запустите один брокер. Для обновлений используйте стратегию остановки прежнего владельца до запуска нового: без перекрытия реплик, с достаточным временем штатного закрытия клиентов. Наличие одной реплики само по себе не исключает перекрытие деплоев.
5. Дождитесь `GET /healthz` брокера со статусом 200. Проверка подтверждает владение Redis и готовность сервиса, не подключается к Telegram и не доказывает авторизацию каждого аккаунта. При потере владения возвращается 503; повторный захват автоматически не выполняется.
6. Проверьте API `/api/health`, соответствие runner ID, внутренний маршрут runtime → API и API → broker на синтетическом транспорте. Health frontend не доказывает работу этих путей. Наличие процесса watcher также не доказывает готовность runner.
7. Включите `PROJECT_TELEGRAM_ACCOUNTS_ENABLED=1` на API после подготовки. Перенос legacy-привязок — отдельная операция с `PROJECT_TELEGRAM_ACCOUNT_CUTOVER_ENABLED=1` по основному руководству. Смена флага не закрывает старые клиенты и не является переносом сессии.

Реальная приёмка двух ботов на выделенном аккаунте выполняется отдельным согласованным шагом. Успех имитации транспорта не подтверждает сетевую доступность Telegram, пригодность прокси и состояние реальной авторизации.

## События и восстановление

Брокер хранит последние **256 событий на клиент** только в памяти. Это ограниченный хвост `NewMessage` и `MessageEdited`, а не долговечная очередь. Начальная подписка получает текущий курсор без воспроизведения истории; ожидание одного запроса — до 20 секунд, разрешено до 30 чатов подписки. При отставании за пределы хвоста или несовместимом курсоре возвращается `EVENT_CURSOR_EXPIRED`: доставка останавливается с явной ошибкой. Автоматического восстановления потерянных событий из истории нет. Перезапуск брокера теряет буфер; сценарии должны учитывать возможный разрыв доставки и не обещать выполнение ровно один раз.

При неудачном релизе сначала остановите зависимые сценарии и штатно закройте владельца сессии. Откатывать образ можно после подтверждения его выхода; сохраните ключ шифрования и совместимую схему БД. Не удаляйте таблицы аккаунтов и не переключайте ботов на legacy в обход журнала переноса. Для отката привязок используйте предусмотренный rollback, который ждёт отключения общего клиента.

После принудительного завершения или потери Redis singleton остаётся занят: это намеренная защита. Сначала подтвердите остановку **всех** прежних владельцев, затем вручную восстановите ключ по [процедуре восстановления](TELEGRAM_ACCOUNTS.md#единственный-владелец-telegram-сессий). Не очищайте ключ ради успешного healthcheck при живом старом процессе.
