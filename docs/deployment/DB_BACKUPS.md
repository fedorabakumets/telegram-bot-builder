# Бэкапы базы PostgreSQL — `npm run db:backup`

Бэкап снимает дамп любой базы PostgreSQL — панели, базы ботов на Railway или на VPS — и кладёт его в хранилище. Восстановление проверяет дамп и после загрузки сверяет число строк в каждой таблице. Это же основа переезда базы между площадками: бэкап со старого места, восстановление на новом.

## Команды

```bash
# бэкап базы панели (DATABASE_URL)
npm run db:backup

# бэкап другой базы под своей меткой
npm run db:backup -- --url postgresql://... --label railway-tbb-bots

# список бэкапов метки
npm run db:backups -- --label railway-tbb-bots

# восстановление последнего бэкапа в пустую базу
npm run db:restore -- --url postgresql://... --label railway-tbb-bots

# конкретный бэкап; перезапись непустой базы
npm run db:restore -- --url postgresql://... --id 20261001-141147 --force
```

Общие флаги: `--label` (по умолчанию `DB_BACKUP_LABEL` или `panel`), `--storage <id>` (по умолчанию `DB_BACKUPS_STORAGE_ID`), `--keep N` для бэкапа.

## Как устроено

- **Дамп** — `pg_dump --format=custom` (сжатый) без владельцев и прав, чтобы восстанавливаться под любым пользователем.
- **Снимок.** Дамп и подсчёт строк идут в одном снимке базы (`pg_export_snapshot`), поэтому числа строк точно соответствуют дампу, даже если боты в это время пишут в базу.
- **Хранение:** `db-backups/<метка>/<время UTC>.dump`, рядом `index.json` со списком: размер, SHA-256, версия PostgreSQL, строки по таблицам. Список лежит в хранилище, а не в базе панели: бэкап можно найти и восстановить, даже если база панели потеряна.
- **Ротация:** хранится `DB_BACKUPS_KEEP` последних бэкапов на метку, старые удаляются.
- **Восстановление:**
  1. Скачать дамп и сверить размер и SHA-256.
  2. Проверить целевую базу: она должна быть пустой, иначе нужен `--force` (тогда её объекты пересоздаются).
  3. Восстановить одной транзакцией: при ошибке база не меняется.
  4. Сверить число строк по каждой таблице. Расхождение даёт код выхода 2.
- **Пароль** передаётся утилитам через `PGPASSWORD`, а не в аргументах: аргументы процесса видны через `ps`.

## Хранилище

`DB_BACKUPS_STORAGE_ID` — S3 из «Хранилищ» панели (`storage_configs`). Без него бэкапы идут в приватную папку `DB_BACKUPS_DIR` (`.db-backups/`; в Docker её нужно монтировать томом, иначе бэкапы пропадут вместе с контейнером). В дампе есть токены ботов и сессии userbot, поэтому публичное `local-default` (`uploads/`) запрещено. Бакет должен быть приватным и лучше не на той же машине, что и база.

## Автоматический бэкап

`DB_BACKUP_INTERVAL_HOURS=24` — панель делает бэкап своей базы раз в сутки, первый через 5 минут после старта. Ошибки пишутся в журнал с префиксом `[DbBackup]` и работу панели не останавливают.

## Версии PostgreSQL

- `pg_dump` не снимает сервер новее себя, поэтому берётся самая свежая установленная версия: `PG_BIN_DIR`, `/usr/lib/postgresql/<N>/bin` (Debian, Ubuntu), `/usr/libexec/postgresql<N>` (Alpine) или PATH. В образ панели ставится `postgresql18-client`.
- Восстановление в сервер **старше исходного** (например, дамп с 18 в 16) запрещено: PostgreSQL такой переход не поддерживает, схема может не встать. На новой площадке нужна та же версия или новее.
- Если целевой сервер старше утилит (дамп с 16 через `pg_restore` 18 в 16), дамп разворачивается в SQL, из него убираются неизвестные серверу настройки сессии (`transaction_timeout`), и скрипт выполняется через `psql` одной транзакцией.

## Проверено

- База панели (PostgreSQL 16, 34 таблицы) — бэкап в S3 на Railway, восстановление в пустую базу, числа строк совпали. Повторное восстановление без `--force` отклонено, с `--force` прошло.
- База ботов на Railway (PostgreSQL 18, 33 таблицы, бот в это время работал) — восстановлена в PostgreSQL 18 на другой машине, числа строк совпали. В PostgreSQL 16 восстановление отклонено с понятной ошибкой.
- `--keep 2` при трёх бэкапах — остались два последних.
- Испорченный дамп отклонён по SHA-256, целевая база не тронута.

## Ограничения

- Дамп целиком держится в памяти. Для баз в десятки гигабайт нужно потоковое чтение и запись.
- Роли и настройки сервера не переносятся — только объекты базы и данные. Расширения попадают в дамп командой `CREATE EXTENSION`, но должны быть установлены на целевом сервере.
- Встроенные бэкапы Railway (снимки тома, восстановление на момент времени) — отдельная настройка в Railway, этот инструмент их не заменяет и не включает.
