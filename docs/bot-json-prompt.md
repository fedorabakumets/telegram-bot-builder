# Документация Bot Builder для ИИ

Вложенные меню связываются переходами кнопок (`action: "goto"`, `target` следующей keyboard-ноды). К сообщению привязывается только его исходная клавиатура через `keyboardNodeId`; переход по кнопке не переносит кнопки вложенного меню на стартовое сообщение при генерации.

Для inline-кнопки с `customCallbackData` генератор создаёт отдельный виртуальный callback-триггер. Целевая `message`-нода продолжает слушать свой идентификатор; явный `callback_trigger` с тем же значением имеет приоритет и исключает дублирование обработчиков.
Динамический `customCallbackData` с `{переменной}` создаёт переход по префиксу также для `message`, `start` и `command`; `edit_message` обрабатывает такой префикс сама.

`hideAfterClick` — поддерживаемое поле отдельной inline-кнопки (`data.buttons[i]`), а не keyboard-ноды. Общий обработчик нажатий снимает клавиатуру до запуска целевой ноды независимо от её типа и настройки БД. Сообщение и текст нажатой кнопки сохраняются, цепочка продолжается. `edit_message` в режиме сохранения клавиатуры не восстанавливает снятое меню. Изменение применяется после повторной генерации и перезапуска бота.

Сбор пользовательского ответа в локальную переменную работает при отключённой БД пользователей и без логирования сообщений. Функция времени ответа генерируется независимо от этих настроек; для применения исправления к существующему боту нужны повторная генерация и перезапуск.

Адрес локального Telegram Bot API задаётся окружением запуска `TELEGRAM_BOT_API_URL`, а не полями JSON узлов. Если адрес не задан, бот использует официальный API. Для применения к существующему боту требуется повторная генерация и перезапуск.

В режиме polling при доступном Redis блокировка запуска принадлежит конкретному процессу: её продление и освобождение выполняются только владельцем. При потере блокировки или невозможности подтвердить продление в течение 50 секунд бот останавливается до окончания её 60-секундного срока. Для применения изменения требуется повторная генерация и перезапуск бота.

Перед изменением живого проекта прочитайте
[правила сохранения и конфликтов MCP](mcp/reliability.md).
В компактном профиле найдите действие через `search_actions`, получите его
схему через `describe_actions` и выполните через `call_action`.
Подготовленный JSON не считается сохранённым. Проверяйте подтверждение
`persistence.confirmed`, ревизию и отдельные статусы live-доставки и применения
ботом. При конфликте перечитайте проект; неизвестный исход внешнего действия
не разрешает слепой повтор с новым идентификатором запроса.

`inputTargetNodeId` задаёт переход после ввода, но сам не включает сбор ответа.
Оставшееся поле в `message` с выключенным или отсутствующим `collectUserInput`
не должно создавать input-ноду при загрузке. Для новых сценариев используйте
отдельный `input`; активные старые `message` с `collectUserInput: true`
сохраняют совместимость.

Для `psql_query` допустимы форматы результата `first_row`, `json`, `text` и `affected`. Форматы `bot_table` для SQL-ноды не подходят и отклоняются при генерации.

В `set_variable` режимы `lookup`, `str_replace`, `json_push` и `json_format` задаются в поле `mode` отдельного присваивания.

Если у `schedule_trigger` нет поля `rules`, генератор применяет интервал пять минут; для других расписаний задавайте правила явно.

Для отправки файлового результата `convert_file` укажите в `message` единственное вложение `attachedMedia: ["{имя_переменной}"]` без других полей медиа. Данные файла декодируются из base64 и отправляются документом.

В `userbot_click_button` источник `messageIdSource: "last_message"` совместим с режимом `"last"`; для заданного идентификатора используйте `"manual"` и `messageId`. Настройки узлов юзербота сохраняются при проверке схемы проекта.

# Секретные ссылки входа

Для `/start link_…` генератор скрывает код в логах, аналитике и истории сообщений. Проверяйте исходное сообщение в code-ноде; не сохраняйте и не выводите код.

### Метаданные исходящих фотографий

При включённой истории сообщений генератор сохраняет `photo.file_size` из ответа Telegram для `bot.send_photo`, `message.answer_photo` и `send_photo_with_caption`. Размер берётся у наибольшего варианта фото (`photo[-1]`) и записывается рядом с его `file_id`, шириной и высотой. Если Telegram не вернул размер, сохраняется `null`; значение нельзя выдумывать или заменять нулём. Новые настройки ноды не требуются. Изменение применяется к новым отправкам после повторной генерации и перезапуска бота; старые записи автоматически не дополняются.
<!-- Связь исходящих сообщений с блоком сценария. -->
При включённой истории сообщений генератор передаёт ID message-блока при отправке текста, фото, видео, аудио, документов и альбомов, включая Telegram file_id и повторную отправку из кэша. Каждый элемент альбома сохраняется отдельно с тем же `node_id`. Это позволяет определить блок отправки в истории файлов; старые сообщения без `node_id` автоматически не восстанавливаются. Эта связь отличается от поиска текущих использований URL файла в сценарии.

Для обложки видео `thumbnailFileIds` имеет приоритет перед `thumbnailUrls`. Если задан готовый `file_id`, URL обложки не используется и не записывается в кэш из ответа Telegram.

## Аналитика v2

Reply- и inline-клавиатуры сохраняются в истории вместе с исходящим сообщением. Session middleware берёт reply-клавиатуру из запроса отправки: Telegram не возвращает её в Message. Повторное логирование обёртками только дополняет недостающие метаданные и ID блока, сохраняя одну запись и один аналитический факт.

При включённой базе пользователей аналитика записывается на границе реальных Telegram-событий, а не переходов между нодами. Пользователь — человек, написавший в личный чат, нажавший настоящую callback-кнопку, адресовавший команду текущему боту, вызвавший принятую команду или ответивший на сообщение этого бота. Переписка группы остаётся отдельным наблюдением. `MockCallback`, исходящие и служебные события не создают пользователя.

Исходящие сообщения считаются только после успешного ответа Telegram, включая стикеры, голосовые, GIF и элементы альбома. Вызовы ручного логирования без Telegram ID не добавляют вторую отправку. Все записи дедуплицируются по идентичности сообщения/callback в общей SQL-транзакции.

Для настоящего нажатия история сохраняет `callback_query_id`; переходы между нодами его не создают. Команда с адресатом в группе должна иметь допустимое имя из латиницы, цифр и `_`, длиной до 32 символов: произвольный текст `/bad!@bot` не подтверждает использование бота. Обычная зарегистрированная команда подтверждается результатом Command-фильтра, а не совпадением текста.

Успешные `forwardMessage`, `copyMessage`, `forwardMessages` и `copyMessages` также учитываются; каждый возвращённый MessageId — отдельная отправка. Предпочитайте числовой chat_id: он не требует дополнительного запроса. При копировании на `@username` после отправки выполняется getChat с таймаутом 2 секунды; если числовой адрес установить не удалось, доставка остаётся успешной, а пропуск учёта явно журналируется. Неизвестный тип отрицательного чата не объявляется группой. Правки сообщений не увеличивают число отправок.

Для `/start` порядок пользовательских exact/startsWith сохраняется. Новая атрибуция использует зарегистрированную короткую метку, а не предположение по `ref_`. Старые `deep_link_param` и `referrer_id` сохраняют совместимость и не являются подтверждённой атрибуцией v2. `link_` — назначение входа, а не доказательство рекламного источника. Исходный `command.args` доступен обработчику; настроенная переменная авторизации существует в памяти во время обработки и удаляется после неё. В стандартную историю, профиль и уведомления записывается `link_[скрыто]`. Не записывайте секрет отдельно через пользовательский SQL/код.

Работающему боту нужны повторная генерация и перезапуск для начала покрытия v2. Старое наличие профиля само по себе не доказывает дату первого взаимодействия.

До PostgreSQL минимальный факт фиксируется в локальной очереди. Сбой БД или реестра оставляет его для повторной доставки после восстановления/перезапуска; ошибки не становятся «без метки». Очередь не содержит текстов, callback payload или кодов входа. `observed_tag` — публичная метка до 64 символов, `link_` даёт только статус `auth_candidate`. Для production `ANALYTICS_SPOOL_DIR` должен указывать на постоянный том; по умолчанию используется `~/.botcraft/analytics-spool/{projectId}/{tokenId}`. Очередь не заменяет резервирование диска.
# Узел исключения пользователя

Узел `kick_user` обрабатывается отдельным шаблоном исключения пользователя.


### Управляемые медиа и хранилища

Для файлов проекта используйте сохранённые относительные адреса `/uploads/...`; не заменяйте их временными подписанными ссылками S3. Внешний URL остаётся внешним URL, даже если в его пути встречается `/uploads/`. Источник прикреплённого файла определяется по его записи, поэтому смена выбранного хранилища не переносит и не удаляет старые вложения. Успешная загрузка, сохранение ноды и запуск бота не подтверждают отправку файла в Telegram.

Вновь сгенерированный бот подтверждает запуск после проверки Telegram и получения доступной Redis-блокировки в режиме polling. Если Redis недоступен, запуск возможен без защиты от двойного запуска; старый сгенерированный код подтверждает запуск по прежнему протоколу.

### Резервная отправка текста при отсутствующем медиа

Если исходник вложения не найден (`MediaNotFoundError`), узел `message` отправляет непустой текст без медиа, сохраняя форматирование, кнопки, тему чата и привязку к узлу в истории. Это происходит только до первой успешной отправки в данный чат: сбой дополнительных вложений или клавиатуры альбома не создаёт повтор основного сообщения. При пустом тексте, ошибке доступа, таймауте и сбое хранилища резервная отправка не выполняется; ошибка остаётся в журнале. Сохранённый Telegram `file_id` используется первым; если он устарел, бот пробует исходник и только при его подтверждённом отсутствии переходит к тексту.
