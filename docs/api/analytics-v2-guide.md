# Аналитика v2: API и данные

Все запросы требуют сессионную cookie или `Authorization: Bearer <PAT>` и доступ к проекту. Связанные боты, источники, размещения, ссылки и расходы проверяются в области проекта. Секрет Telegram-токена не возвращается.

## Снимок и определения

`GET /api/projects/12/analytics/v2/snapshot?period=7d&comparison=previous&timezone=Europe%2FMoscow`

Один ответ содержит общий `as_of`, строковую `revision`, `range`, `current`, `previous`, `points`, `leaders`, `sources`, `source_points`, `buttons`, `availability`, `composition` и `next_recompute_at`.

- Пользователь подтверждается личным сообщением, реальным callback, направленной командой или ответом текущему боту.
- `new_users` — первое известное подтверждённое действие внутри `[from,to)`; `total_users` — всё время.
- `restored_users` — первое **датированное сохранённое свидетельство контакта** попало в окно, но фактическое начало использования не установлено (`known=false`). Это отдельное поле API для восстановленной истории; её нельзя складывать с `new_users` и называть новыми пользователями.
- `active_users` — уникальные люди с физическим событием либо аудированным историческим свидетельством контакта за всё окно; сумму дневных уникальных использовать нельзя.
- `returning_users` контактировали в окне и имеют сохранённое свидетельство **до начала окна**. Повторный контакт впервые пришедшего внутри этого же окна не делает его вернувшимся. `unknown_first_users` — вся подтверждённая аудитория без доказуемой первой даты, независимо от выбранного периода.
- `messages.total = incoming + outgoing`; callback и служебные события отдельны.
- `leaders.groups` отражает направленные действия, `groups_observed` — наблюдаемую групповую переписку, ограниченную настройками Telegram.
- `availability` и `composition` — текущие снимки, не восстановленные свойства профиля на старую дату.

Можно задать `period=1h|3h|24h|7d|30d|12w|12m|all` либо обе ISO-границы `from` и `to` с часовым поясом. `12w` — 84 суток, `12m` — 365 суток. Шаг независим: `1m|5m|1h|1d|7d|30d`, максимум 500 точек. Для `all` шаг укрупняется автоматически, `previous=null`.

Суточные и более крупные интервалы привязаны к календарной сетке `range.timezone`; день начинается в местную полночь. `points[].date` и `points[].end_date` передаются в UTC и обозначают фактические полуоткрытые границы слота. При смене летнего времени суточный слот может длиться 23 или 25 часов, поэтому его конец нельзя вычислять как `date + step_ms`: используйте `end_date`. Старый снимок может не содержать это дополнительное поле. `source_points` использует те же границы. Шаги меньше суток сохраняют фиксированную длительность; исходные `from/to` и итоговые числа периода не меняются. Счётчики крайних слотов ограничены `[from,to)`, даже если календарная граница находится за пределами окна.

`coverage.status` принимает `complete`, `partial`, `unavailable`; ответ включает начало покрытия каждого бота и текст причины. Нулевая цифра при неполной истории не доказывает отсутствие старых пользователей. Новая методика начинается после повторной генерации и запуска бота. Старая переписка и переменные `deep_link_param` сами по себе не подтверждают первую атрибуцию.

`current.audience.first_history_status` и, при сравнении, `previous.audience.first_history_status` описывают полноту первых взаимодействий в соответствующем окне (`complete|partial|unavailable`). Наличие `restored_users` всегда означает `partial`. В `points[]` есть отдельное поле `restored_users`; проектный итог дедуплицирует человека по самой ранней сохранённой дате среди всех ботов, ботный — внутри выбранного бота. Повторное действие не добавляет ещё одного восстановленного человека.

Иллюстрация поля `audience`:

```json
{
  "new_users": 200,
  "restored_users": 25,
  "total_users": 3077,
  "active_users": 240,
  "returning_users": 15,
  "unknown_first_users": 407,
  "first_history_status": "partial"
}
```

Восстановление не делает неизвестную первую дату достоверной. `sources[]` и `source_points[]` показывают источники первых сохранённых взаимодействий, отдельно сохраняя точные `new_users` и восстановленные `restored_users`. Их сумму можно отображать как первые сохранённые взаимодействия, но нельзя называть точным привлечением. Цена привлечения использует только подтверждённые новые: серия `restored_users` в её знаменатель не включается.

### Аудированная старая история

Отдельный перенос свидетельств сохраняет только идентификаторы области и человека, ID старой строки, основание, тип чата и время сохранения. Старые callback без Telegram ID не превращаются в физические нажатия: они могут подтверждать контакт человека при совпадении со строго проверенной формой старого писателя. Количество физических сообщений и callback от таких свидетельств не растёт. В популярности кнопок `historical_count` учитывается отдельно; интерфейс может суммировать его с `count` в режиме «Нажатия». Рейтинги людей используют сохранённые свидетельства без создания физических действий. Для адресной команды нужны физический ID сообщения и исторический username текущего бота; обычная переписка, упоминание и неадресная команда доказательством не становятся.

Политика переноса фиксирует проект, бота, SHA256 исследованной сборки, исторический username и верхний ID проверенной истории. Ограничение `audited_writer_shape_without_per_row_build_identity` означает, что версия каждой старой строки не сохранилась: fingerprint файла и совпадение формы не выдают за полноценный журнал запусков. Время старой записи — время её сохранения, а не доказанное первое использование.

Если найдено более раннее свидетельство, прежняя поздняя «точная первая дата» становится восстановленной. Первая атрибуция сбрасывается в неизвестную; позднее физическое событие с источником остаётся возвращением по ссылке. Для проекта человек учитывается один раз; при одинаковых первых датах неопределённая история имеет приоритет над точной.

Для дополнительной проверки конкретной исторической сборки перенос также запускается отдельно через `scripts/backfill-analytics-evidence-v2.ts`: обязательны `--project`, `--token`, `--through-message-id`, `--historical-username`, `--writer-sha256` и `--artifact`. Без `--apply` выполняется только согласованный предпросмотр агрегатов; с `--apply` запись идёт пачками с независимой контрольной точкой. Завершённый прежний перенос событий не мешает этой проверке. Повтор не добавляет человека или свидетельство дважды. Очистка переписки сохраняет свидетельства; полное удаление человека очищает их, а watermark запрещает восстановление старых строк повторной доставкой.

### Источники старых `/start`

Наблюдаемая метка восстанавливается из сохранённого `/start` и связывается с физическим Telegram-сообщением в области проекта и бота: совпасть должны чат и идентичность сообщения. Чтобы назвать её источником первого сохранённого взаимодействия, это должно быть **то же физическое сообщение**, которое подтверждает первое взаимодействие. Совпадения пользователя, текста либо близкого времени недостаточно. Повторная запись одного сообщения не создаёт второй вход.

Поздний `/start` с другой меткой остаётся повторным входом. Он может участвовать в счётчиках запусков и возвращений по ссылке, но не переписывает первый источник и не создаёт ещё одного нового или восстановленного человека. Текущее значение `deep_link_param` в профиле не заменяет источник исторического первого события.

Наблюдаемая метка, зарегистрированный рекламный источник и подтверждённый пригласивший — разные данные. Неизвестный источник остаётся явно неизвестным; метку нельзя автоматически приравнивать к зарегистрированному размещению. Значения `ref`, `ref_*` и числовой суффикс не доказывают пригласившего без зарегистрированной связи. Восстановленная метка не повышает точность неизвестной первой даты и не включает `restored_users` в CPA.

Параметры авторизации `link_` исключаются из сохраняемых наблюдаемых меток и из выдачи источников. Исходный секрет не копируется в аналитические факты, стандартные журналы, Redis, WebSocket или MCP. Безопасное назначение авторизационного перехода не раскрывает код входа и само по себе не подтверждает рекламное происхождение.

## Простая ссылка и рекламный бюджет

В текущем UI пользователь выбирает бота и вводит метку: `https://t.me/<username>?start=raspred`. Получение и копирование такой ссылки — локальная операция, без POST и без регистрации источника. Открытие ссылки не равно подтверждённому запуску. Текст метки сравнивается точно. Одна метка у одного бота объединяет публикации; для независимой рекламы нужна другая метка.

Необязательный рекламный бюджет сохраняется через защищённый endpoint:

```http
POST /api/projects/12/analytics/acquisition/budgets
Content-Type: application/json

{"tokenId":3,"marker":"raspred","amount":"3000.00","currency":"RUB","day":"2026-11-01","timezone":"Europe/Moscow"}
```

Все поля обязательны. `tokenId` — положительный ID бота текущего проекта, `marker` — 1–64 символа `[A-Za-z0-9_-]`, `amount` — неотрицательная decimal-строка до двух знаков после точки, `currency` — `RUB|USD`, `day` — календарная дата, `timezone` — IANA-пояс. Неизвестные поля отклоняются. Префикс `link_`, `ref` и `ref_*` запрещены: endpoint не создаёт коды авторизации или реферальные связи.

Сервер в одной транзакции проверяет проект/бота, находит либо создаёт источник и технические связи `placements`, `links`, `analytics_placement_history_v2`, затем записывает дневной расход и аудит. Возвращает HTTP 201 и `{ "item": { ... } }` — одну созданную запись расхода. Формат совпадает с `expenses.item` в OpenAPI. Простая форма не передаёт курс: его можно добавить позднее через PATCH расхода.

Повторный POST с той же меткой добавляет **новую финансовую запись**. Это не идемпотентный запрос и не замена старой суммы; при неясном результате сначала проверьте каталог, не повторяйте автоматически. Существующая метка сохраняет прежние `startsOn` и пояс. Новая дата расхода не создаёт новую кампанию и не переносит границу старого прихода. Если обнаружена прежняя историческая привязка, она используется повторно. Демонстрационные исторические привязки имеют особый режим и не выдают старый приход за новое точное привлечение.

HTTP 400 — некорректные поля, зарезервированная метка либо архивный источник/связь; 401 — нет авторизации; 403 — нет доступа к проекту; чужой/отсутствующий бот отклоняется внутри проекта. HTTP 409 — конфликт `exact`/`startsWith` маршрута `/start`, архивная публичная ссылка либо уже занятая ссылка другого назначения; никаких частичных записей не остаётся. HTTP 503 — временный сбой. Проверка конфликта происходит при сохранении бюджета, а не при локальном показе обычной ссылки.

Термин **«Источник»** объединяет пользовательское представление; HTTP и MCP сохраняют технические `sourceId`, `placementId`, `expenses` для совместимости. Старый расширенный API регистрации ссылок ниже остаётся доступен, но не описывает шаги текущего простого UI.

## Совместимый API зарегистрированных ссылок

Используйте ID из фактических ответов. Ниже числа иллюстративные.

```http
POST /api/projects/12/analytics/acquisition/sources
Content-Type: application/json

{"name":"Канал партнёра","kind":"telegram","url":"https://t.me/example"}
```

```http
POST /api/projects/12/analytics/acquisition/placements
Content-Type: application/json

{"name":"Публикация 1 ноября","sourceId":4,"tokenId":3,"startsOn":"2026-11-01","timezone":"Europe/Moscow"}
```

```http
POST /api/projects/12/analytics/acquisition/links
Content-Type: application/json

{"placementId":6,"purpose":"acquisition"}
```

Сервер вернёт `{ "item": { ... } }` с постоянным `code` и URL `https://t.me/<bot_username>?start=bc_<code>`. Для совмещения рекламы и реферала передайте `purpose=combined` и `referrerId` подтверждённого пользователя проекта. Произвольный `ref_123` не является доказательством реферера.

`link_` зарезервирован существующим входом на сайт. Рекламный конструктор не создаёт коды авторизации. Сам вид параметра не подтверждает рекламную площадку или успешный вход. Повторная рекламная ссылка не переписывает первоначальное привлечение.

## Рекламный бюджет и цена пользователя

```http
POST /api/projects/12/analytics/acquisition/expenses
Content-Type: application/json

{"placementId":6,"day":"2026-11-01","amount":"3000.00","currency":"RUB","allocation":"single"}
```

Для распределения на несколько дней явно задайте `allocation=equal` и `untilDay`. Ответ `{ "items": [...] }` содержит дневные записи; сумма сохраняется точно, распределение помечено `estimated=true`.

Сумма и курс передаются строками. `exchangeRateRubPerUsd="95.12345678"` означает **95.12345678 RUB за 1 USD**. `exchangeRateDate` — дата фиксации; по умолчанию первый день рекламного бюджета. Курс сохраняется в записи. Его можно получить через официальный API ЦБ и явно применить к оплате; автоматического пересчёта прежних записей нет. Исправления доступны в истории.

`GET /api/projects/12/analytics/acquisition/report?from=2026-11-01T00%3A00%3A00%2B03%3A00&to=2026-11-02T00%3A00%3A00%2B03%3A00&currency=RUB`

Без `from/to` отчёт показывает весь срок. Ответ содержит `asOf`, границы, `lifetime` и технические строки размещений. `returningUsers` — уникальные люди с первым сохранённым контактом до `from`, совершившие в окне направленный вход (`metadata.entry=true`) либо сохранённый `/start` по метке. Обычное личное сообщение без входа сюда не включается. `repeatStarts` хранит повторные запуски отдельно; впервые пришедший в этом окне может повторно запуститься, не увеличивая `returningUsers`. Первоначальная атрибуция сохраняется. Один человек может попасть в возвраты нескольких источников: суммы строк не равны уникальному итогу проекта. Пример строки:

```json
{
  "newUsers": 200,
  "returningUsers": 12,
  "repeatStarts": 15,
  "spend": {"RUB":"3000.00","USD":null},
  "convertedSpend":"3000.00",
  "costPerUser":"15.00",
  "costPerUserByCurrency":{"RUB":"15.00","USD":null},
  "currency":"RUB",
  "complete":true,
  "reason":null,
  "estimated":false,
  "currentDay":false
}
```

Нулевой указанный расход отличается от отсутствующего. `costPerUser=null` означает, что точную цену показать нельзя: отсутствует расход, курс или новые пользователи, история неполна либо окно обрезает день рекламного бюджета. Дневная оплата автоматически не распределяется по часам. `estimated` отмечает оценочное распределение, `currentDay` — результат на текущий момент. Исходные RUB/USD не смешиваются. Telegram-запуски не являются кликами; CTR и ROI не рассчитываются.

`costPerUserByCurrency` сохраняет отдельную цену в RUB и USD. Отсутствующий курс мешает сводному пересчёту, но не делению исходной суммы на подтверждённых новых пользователей: например, `USD="2.50"` остаётся доступным при `costPerUser=null` и пояснении об отсутствующем курсе в `reason`. Неизвестная история, неполный день, отсутствие расхода в этой валюте или новых пользователей дают `null` и в отдельной цене.

В отчёте всего проекта точная цена требует покрытия всех ботов выбранной области: обновление только бота размещения не доказывает, что человек ранее не пользовался другим ботом проекта. Для отчёта одного бота полнота проверяется в его области.

## Исправления и история

Для каждого ресурса `sources|placements|links|expenses` доступны список, создание, `PATCH /:resourceId` и `GET /:resourceId/history`. История содержит автора, время, `beforeData` и `afterData`.

`{"archived":true}` архивирует, `false` восстанавливает. Опубликованная метка не меняется при переименовании источника. Поля связей и коды ссылок нельзя перепривязать через PATCH.

## WebSocket, Redis и восстановление

Общий `/api/terminal` проверяет сессию и доступ к проекту. Изменение аналитики приходит как проектное уведомление:

```json
{
  "type":"analytics-changed",
  "projectId":12,
  "data":{"revision":"42","affected":["audience","acquisition"]},
  "timestamp":"2026-11-02T10:00:00.000Z"
}
```

Это сигнал получить новый снимок, а не набор чисел для прибавления. Объединяйте серию уведомлений; при reconnect и возврате вкладки запрашивайте актуальный ответ. Для скользящего окна установите один таймер по `next_recompute_at`. Статус «Обновлено» означает полученный снимок.

PostgreSQL хранит факты, версии и outbox в одной транзакции. `LISTEN/NOTIFY` пробуждает обработчик; после разрыва он сверяет сохранённые версии. Redis обслуживает оперативный обмен платформы и старую ленту. Его сбой не удаляет уже записанные факты. Дедупликация основана на Telegram identity. Очистка переписки не удаляет аналитику; удаление проекта удаляет её.

## Ошибки и совместимость

| Код | Значение |
|---|---|
| 400 | Неверные поля, диапазон, сумма или шаг; проверьте `message` и `issues` |
| 401 | Нет авторизации |
| 403 | Чужой проект или бот |
| 404 | Ресурс отсутствует в проекте |
| 409 | Метка пересекается с пользовательским маршрутом `/start` |
| 503 | Временная недоступность; не заменяйте ошибку нулевыми числами |

Старые endpoints и инструменты сохраняют прежние определения. Для новой вкладки используйте v2. OpenAPI обновляется через регистрацию `analytics-v2`; экспорт без запуска сервера: `npx tsx scripts/export-analytics-contracts.ts`.


Если первое подтверждённое событие человека — настоящий callback кнопки в группе или супергруппе, отчёт источников показывает «Группа · название». Стабильный ID имеет вид `group:<token_id>:<chat_id>`; переименование меняет только подпись. При отсутствии названия используется ID чата. Название берётся только из той же области проекта и бота. Обычная переписка и более поздние нажатия не меняют первый источник; проектный отчёт по-прежнему выбирает самое раннее взаимодействие человека среди ботов. Это место первого взаимодействия, а не подтверждённое рекламное размещение: source_id, расходы и CPA не изменяются. Старые нажатия без подтверждённой физической идентичности автоматически источником группы не становятся.


`token_audiences` в снимке содержит `token_id` и `total_users` для всех ботов текущего проекта. Это подтверждённая аудитория за всё время, независимо от выбранного периода и конкретного бота отчёта; счётчики предназначены для селектора и обновляются вместе со снимком. Сумма по ботам не равна уникальной аудитории проекта.


Первое подтверждённое входящее сообщение в личном чате, включая `/menu` и обычный текст, без наблюдаемой метки и установленного источника относится к «Без метки источника». Это отсутствие метки, а не доказанный прямой переход. Авторизация, реферальные состояния, зарегистрированный источник и сохранённая метка имеют приоритет; поздние события первоначальный источник не меняют.


Миграция `0032_analytics_private_no_marker.sql` при старте уточняет прежние записи аудитории с неизвестным источником и первым подтверждённым личным сообщением. Она сохраняет даты, `first_known`, факты, расходы и атрибуцию; наблюдаемые метки и авторизация исключены из обновления. Повтор миграции не создаёт повторного уведомления. Фоновый перенос новых старых строк сразу использует это правило.


Аудированное историческое нажатие, ставшее первым сохранённым свидетельством, получает источник по известному чату: личка — «Без метки источника», группа — «Группа · название». Идентичность группы включает бота; при отсутствии ID группы источник остаётся неизвестным. Миграция `0033` уточняет прежние личные свидетельства, не изменяя события, первые даты и точность истории. Счётчик физических callback от этого не растёт.


Рейтинг групп по взаимодействию сортируется по уникальным людям, имевшим направленный контакт в группе за период, включая аудированные исторические свидетельства. Один человек в нескольких записях или у нескольких ботов проекта считается в этой группе один раз. В API `leaders.groups[].people` содержит число людей; `total`, `messages`, `callbacks` сохраняют прежний смысл физических действий. Старые свидетельства их не увеличивают. Наблюдаемая переписка остаётся отдельным режимом. Уже перенесённая история используется автоматически без повторного создания событий или изменения расходов.


`leaders.groups_observed[].people` — уникальные авторы наблюдаемых сообщений группы за окно; рейтинг сортируется по этому полю. `messages` и `total` сохраняют прежнее число сообщений. Один автор с несколькими сообщениями считается один раз.


Популярные кнопки имеют режимы «Нажатия» и «Люди». `buttons[].people` объединяет реальные callback и аудированные исторические свидетельства по человеку и подписи кнопки; повторные записи не увеличивают число людей. `buttons[].count` сохраняет точное число физических callback. Миграция `0034` переносит только безопасную подпись кнопки в независимую историю; очистка переписки её не удаляет. Callback payload и параметры `link_` не переносятся. При отсутствии подписи используется «Кнопка без названия». Подписи объединяются по тексту, поэтому одинаковый текст в разных нодах не разделяется.


По принятой пользователем методике каждая аудированная старая запись кнопки считается нажатием. В режиме «Нажатия» интерфейс показывает сумму `buttons[].count` и `buttons[].historical_count`; режим «Люди» использует `people`. В подробностях составляющие разделены: с Telegram ID и из старой истории. Старые записи не переименовываются в физические callback и не меняют существующий контракт `count`. API возвращает до 100 подписей по числу нажатий, интерфейс показывает первые 20 по выбранному показателю. Новая миграция не нужна: применённая `0034` уже сохраняет необходимые подписи.


Карточка «Группы по сообщениям» отдельно ранжирует группы по числу наблюдаемых входящих сообщений за общий период (`leaders.groups_messages`). Она не зависит от режима соседнего рейтинга людей. В подробностях доступны число сообщений, уникальные авторы и переход в переписку группы. Callback и исходящие ответы бота не включены. Топ считается на сервере по сообщениям, а не пересортировкой усечённого топа по людям.


Размещение может быть явно связано с исторической меткой через `analytics_placement_history_v2` (миграция `0035`). Первые сохранённые обращения возвращаются отдельно как `historicalUsers`, не увеличивая `newUsers` и не меняя первоначальную атрибуцию. Повторные входы по метке учитываются в возвратах и повторных запусках. Для демонстрационной связи `isDemo=true` допускается `demoCostPerContact` — условная цена исторического контакта, только за полные календарные дни или весь срок. Она не является точной CPA. В интерфейсе видны отметки «Из истории» и «демо». Токены авторизации в привязку не допускаются.


Указанные дневные расходы в `spend` и их доступный пересчёт не скрываются из-за неполного календарного окна. При пересечении дня рекламного бюджета показывается указанная сумма дня целиком, без почасового распределения. Неполное окно по-прежнему запрещает расчёт CPA и демо-цены; причина доступна в отчёте.


В интерфейсе рекламный отчёт переводит готовый период в календарные дни своего часового пояса: 7 дней — текущий и шесть предыдущих; 30 дней — текущий и 29 предыдущих; 12 недель — 84 дня; 12 месяцев — 365 дней. Часовые варианты показывают текущий календарный день. Конец текущего дня ограничен моментом общего снимка и помечен «На текущий момент». У отчёта явно показаны собственные границы. Графики аудитории сохраняют исходное скользящее окно. Явные календарные даты не меняются, а для всего времени начало округляется к местной полуночи первого дня. HTTP API по-прежнему принимает точные UTC-границы без неявного округления; MCP получает тот же контракт.


Таблица источников в интерфейсе автоматически включает найденные источники без размещений. HTTP/MCP: `includeSources="true"` добавляет такие строки; без параметра прежний контракт размещений сохраняется. У автоматической строки `placementId=null`, `rowKey` — стабильный ключ, `sourceKey` — ключ источника; `sourceId` может отсутствовать (`null`) у исторической метки или статуса, `tokenId=null` означает весь проект. Расход отсутствует (`null`), а не равен нулю. Источники, уже связанные с размещениями или историческими метками, второй строкой не дублируются. Открытие таблицы не создаёт размещений и финансовых записей. Весь найденный список виден и при отсутствии контактов в выбранном окне.


## Бесплатный курс USD/RUB для рекламного бюджета

`GET /api/projects/{id}/analytics/acquisition/exchange-rate?day=2026-11-01` требует обычной авторизации и доступа к проекту. Ключ внешнего API не требуется. Ответ: `{"requestedDay":"2026-11-01","effectiveDay":"2026-10-31","rubPerUsd":"80.55730000","source":"cbr","sourceUrl":"https://www.cbr.ru/development/sxml/"}`. Значение приведено как пример фактически полученного ответа. Поставщик — официальный XML API Банка России; направление — RUB за один USD, номинал учтён, число передаётся decimal-строкой. Для выходных сохраняйте `effectiveDay`, не подменяя её датой запроса. Передайте курс и эту дату в `exchangeRateRubPerUsd` и `exchangeRateDate` при явном сохранении расхода. HTTP 400 — некорректная или будущая дата; 503 — сбой поставщика, тайм-аут или некорректный ответ. В этих случаях курс не выдумывается, доступен ручной ввод. Запрос передаёт поставщику только день, без данных проекта.

### Атомарный автоматический перенос истории

После подготовки HTTP сервер выполняет оставшуюся сохранённую историю одной транзакцией: события, наблюдавшиеся источники и контрольные точки фиксируются вместе. До завершения другие соединения видят предыдущие данные; промежуточные результаты не публикуются. Ошибка или остановка откатывает весь текущий запуск, а повтор использует ранее завершённые контрольные точки. Новые сообщения не продлевают захваченные верхние границы. Чтение внутри операции ограничено по размеру, но промежуточных commit и пауз между порциями нет. Большой перенос может временно задерживать конкурирующую запись аналитики; PostgreSQL остаётся источником фактов, повторная доставка идемпотентна.


### Автоматическое восстановление старых взаимодействий

При запуске конструктора общий атомарный перенос обрабатывает все проекты и ботов: физические события, строгие свидетельства старых нажатий и адресных команд, затем метки `/start`. Все результаты публикуются одним commit. Повторный запуск использует сохранённые курсоры; новая история продолжает перенос без повторного подсчёта. Ошибка откатывает все три части.

Для автоматической политики используются строгая структура старой записи и текущий сохранённый username бота. Боты без корректного username пропускаются; для истории переименованного бота доступен отдельный перенос с явно проверенным историческим username. Fingerprint автоматического задания обозначает версию правил, а не наличие известной сборки у каждой старой строки. Обычная переписка групп и команды другому боту не подтверждают использование. Старые записи без Telegram callback ID сохраняются как исторические свидетельства, не как физические события; настоящая дата первого использования остаётся неизвестной.


Операция `POST .../acquisition/budgets` также принимает необязательные `exchangeRateRubPerUsd`, `exchangeRateDate`, `note`, `untilDay`, `allocation` по контракту расходов. Для нескольких дней требуется `allocation: "equal"`; дневные части сохраняют общую сумму, курс и примечание. Создание метки и всех частей бюджета остаётся одной транзакцией.
