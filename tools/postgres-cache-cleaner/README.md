# Очистка файлового кеша PostgreSQL

Production-сервис `postgres-cache-cleaner` (`d1b872a0-0cef-4835-9418-63c4c75c6062`)
запускается по расписанию `*/10 * * * *`. Образ `postgres:18-alpine` используется
только как клиент psql. После вызова операция завершается; постоянно работающего
процесса нет. Ограничение сервиса — 100 МБ и 0,1 vCPU.

Операция `tbb_cache_maintenance.release_os_file_cache()` выполняется внутри
контейнера PostgreSQL. Она передаёт ядру POSIX_FADV_DONTNEED для обычных файлов
в PGDATA/base, global и pg_wal. Файлы открываются только для чтения, символические
ссылки пропускаются. Файлы базы не удаляются, PostgreSQL не перезапускается.
Буферы PostgreSQL и занятые/грязные страницы принудительно не очищаются.
Кеш может снова вырасти между запусками; первые чтения после очистки могут замедлиться.

Роль tbb_cache_cleaner имеет доступ только к этой операции; права суперпользователя
и pg_execute_server_program ей не выдаются. Функция SECURITY DEFINER принадлежит
postgres, имеет фиксированный search_path и не принимает параметров. Пересечение
запусков исключено advisory lock; установлены таймауты операции и клиента.

`provision.py` — установочный сценарий для этой конкретной production-среды.
Повторный запуск не требуется: существующие роль и схема вызовут ошибку,
транзакция откатится. Секрет создаётся случайно и передаётся Railway через временный
файл; в исходниках его нет. Для отключения достаточно убрать cron-расписание или
удалить только сервис postgres-cache-cleaner. Саму базу останавливать не нужно.
